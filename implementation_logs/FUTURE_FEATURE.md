## #19 — py 組み込みスタブの整備（`time` / `math`）✅ **完了（2026-09-19）**

- **意義**: 型検査の推論が `Unresolved` に落ちる**最大の残存要因**。
  `time.time()` のような **C 実装の py 組み込みモジュール**は `.py` ソースが無く
  スタブを抽出できないため、**型検査の推論規則ではこれ以上詰められない**と結論が出ている。
  ⇒ 潰し方は「推論を賢くする」ではなく「**スタブを置く**」方向（#17-b と同じ）。
- **効果の見込み**: `Unresolved` が減ると binop / call の型特化が乗る。
  ⚠ **数値は測っていない**。着手時は `AR_ANNOT_DIFF=1`（`AnnotUnresolvedSrc`）で
  **現在の発生源内訳を取り直してから**決めること。
- **前提**: なし。
- **手法**: 同梱 `.pyi` を用意する。
  ⚠ **`python_search_dirs()` に置き場を足す案は採らなかった**（実装時の判断）。
  `cargo run` と配布レイアウトで相対位置が変わり「開発中だけ効く」を作り込むうえ、
  **モジュール解決 1 回あたり `exists()` が 4 回増える**（#69 が「`exists()` の syscall
  連打が `interp_init` の 48〜53%」と測っている）。
  ⇒ `include_str!` で**バイナリに埋め込み**、検索ディレクトリを全部見て
  空振りしたときだけ引く（**利用者のファイルが常に勝つ**）。
- **実装**: [`src/py_stubs.rs`](../src/py_stubs.rs) の埋め込み表 ＋
  [`stubs/time.pyi`](../stubs/time.pyi) / [`stubs/math.pyi`](../stubs/math.pyi)。
  例題 `examples/interop/py_int_stub.ar` / `py_int_stub_error.ar`。
- **積み残し**: **モジュール定数の型**（`math.pi`）は拾えないまま（関数だけ）。
  ⚠ 未宣言メンバは従来どおり動く（`math.pi` は壊れない）ことを実測で確認済み。
- **留意点**:
  - ⚠ **グローバル名を占める登録は慎重に。** 組み込み関数の型を型検査のグローバルへ入れると
    `let <name> = ...` が「already declared」の**静的エラーになる**。過去に `len` / `repr` は
    この理由で**意図的に外した**（特化件数の伸び +1 に対して既存コードを壊す割に合わない）。
    `range` だけ登録されているのはループ形の頻度が圧倒的で変数名に使われないため。
  - ⚠ スタブの探索方針は `ar_config.json` 側と**一貫させる**（#72/#74 で読み手を 1 本化した）。
- **参照**: skill `importation`（`import[py]` の実装）／skill `type-checking`（推論規則）／
  実装ログ #16 の「残る miss の主因」。

## #17-b — JS スタブの型付け

- **意義**: **JS は `.ars` に型が書かれて初めて FFI 境界検査が効く**。現状の `.ars` は型を持たず
  **実質無検査**。FFI 境界検査の設計は「**スタブが宣言した型を検査の根拠にする**」向きなので、
  スタブが整うほど強くなる（従来の `CheckBefore` とは逆向きの性質）。
- **前提**: なし。
- **手法**: 既定は `Any`。`.d.ts` があればそれを読んで `.ars` を生成する。
- **留意点**:
  - ⚠ **既定を `Any` にすること**（型が無い状態を「検査しない」に倒す）。
    厳しくすると既存の JS 連携が一斉に落ちる。
  - ⚠ 生成した `.ars` は**キャッシュの鮮度**に注意（`import[cs-dll]` の `.ars` と同じ扱い）。
- **参照**: skill `importation`（`import[js-proc]`）／実装ログ「この機構でも救えない範囲（→ #17 へ昇格）」。

## #17-a — C/C++ の `void*` に専用型を導入

- **意義**: **C/C++ の `void*` は Arrow の `int` に落ちる**。型タグは「int である」以上を語らないので、
  **動的検査を入れても静的型と同じことしか言えない**。⇒ 不透明ハンドル型を導入して
  **int との相互代入を静的に禁止**するのが唯一の前進。
- **前提**: なし。
- **手法**: 不透明ハンドル型（opaque handle）を型検査へ足し、`int` との暗黙変換を禁止する。
- **留意点**:
  - ⚠ **話題は C/C++ 相互運用だが、変更は静的型検査だけ**（実行時表現は変えない）。
    実行時ディスパッチに触ると別タスクになる。
  - ⚠ **既存コードが `void*` を int として扱っている箇所**が壊れる。
    静的エラーを増やす変更なので、**例題とテストの落ち方を先に測る**こと。
  - ⚠ ネイティブ ABI 側の表現（`InstanceData` の raw ブロック等）と整合させる。
- **参照**: skill `c-abi-interop`（C ABI 型注釈と raw レイアウトの設計仕様）／skill `type-checking`。

## #89 — メタプログラミングの前提（`Value → AST` ＋ AST→実行の入口）

- **意義**: 「実行時に AST を組み立てて実行する」ための**足りない 2 つ**を埋める。
  #84〜#85 の評価で、**メタプロが「expr を 1 個足す」で済まない理由は AST 側ではなく
  `Value↔AST` 境界とパイプライン入口にある**と判明している。
- **前提**: ← #84（済）・#85（済）＋ ⚠ **消費者の出現**（現在**居ない**）。
  判定基準は「**消費者が居るか**」（#11 R2-c / #14 / #15b を保留にしたのと同じ基準）。
- **今ある追い風**（着手時に活かす）:
  - **AST は既に第一級の値** — `src/interpreter/ast_value.rs`（Stmt 40 / Expr 29 が exhaustive）。
  - **実行時に AST を作って実行するのは `templates.rs` が実証済み**（型引数キーの Chunk メモ化）。
  - **合成 AST は `node_id: 0` / `Resolution::Unresolved` でも正しく動く**（＝「遅いが動く」が既定）。
  - **パイプラインが `&mut Vec<Stmt>` の独立パス**なので、展開パスは parse と type_check の間に挟める。
- **足りないもの**:
  1. **`Value → AST` の逆変換が無い**（`ast_value.rs` は一方向のみ）。
  2. **AST→実行の入口が無い** — `vm/compiler/entry.rs` の `compile_debug` は
     `Stmt::Expr` / `Stmt::Let` の **2 形だけ**で `_ => return None`。
- **留意点**:
  - ⚠⚠ **`Value` は動的なので match で守れない。** 逆変換を書くと、#59/#81/#84 が塞いだ
    「ドリフトを強制で止める」網の**外側**に大きな面ができる。**#84・#85 の強制点が
    先に要る**と判断したのはこのため。
  - ⚠ 展開パスを足すなら**配線は 1 箇所**（#88 の `resolve_and_annotate`）に足す。
- **参照**: 実装ログ「#84〜#89 …… 結果 ③」（メタプロの追い風/向かい風の全リスト）。

## #90 — Python デコレータの三分岐（メタ関数化 / クロージャ化 / 読み込み時エラー）

- **意義**: `import[py]` が読んだ Python のデコレータを、**変換時に静的分類**して
  ①Arrow のメタ関数（`!`）／②実行時デコレータ（`@`・クロージャ置換）／
  ③読み込み時エラー に振り分ける。現在の `convert_decorators` は
  「定義種別マーカ（`@staticmethod` 等）」と「それ以外」の **2 分岐しか無い**。
  ⇒ 実在の Python コードのデコレータが**どこまで読めるか**の上限を決める項目。
- **前提**: ⚠⚠ **#89（メタプログラミングの前提）が先**。①の行き先である
  Arrow のメタ関数そのものが未実装なので、分類しても受け皿が無い。
  **ユーザー判断（2026-09-19）: メタ関数の実装後に対処する。**
  - ✅ 済んだ前提: **呼び出し側の `*` / `**` 展開**（U4/U5・フェーズ F）——
    これが無いと②が空振りしていた（Python の最も普通のラッパ
    `def w(*a, **k): return f(*a, **k)` が変換時 `ParseError` だった）。
  - ✅ 済んだ前提: **Python モジュール内 import の再帰ロード**（項目27）——
    他モジュール定義のデコレータも、その `.py` が検索パスにあれば分類できる。
  - ⏳ 残る前提: **禁止機構の検出**（`setattr` / `type()` / `__dict__` 操作 /
    ディスクリプタ）と、**①のホワイトリスト**（`@dataclass` 等）。
- **留意点**:
  - ⚠⚠ **「まず①を試し、失敗したら②へ」という動的フォールバックにはできない。**
    `import[py]` は**パース時**に解決され、メタ関数の展開はその後なのでフェーズをまたぐ。
    規約（#3「フォールバックは無い」）とも衝突する ⇒ **変換時の静的分類**にする。
  - ⚠ **①は一般判定ではなくイディオムのホワイトリスト。** メタ関数化とは
    「Python の命令的コードを AST 操作コードへ翻訳する」ことで、
    `def log(f): def w(*a, **k): ... return w` を `^f.params` のスプライスに直すには
    **意味を理解する**必要がある。機械的変換ではない。
  - ⚠ **③の保証は完全にはできない。** stdlib / サードパーティのデコレータ
    （`@app.route` / `@lru_cache`）は本体が読めないので禁止機構を検出できない。
    ただし項目27 以降は **import の時点で明示エラー**になるので、
    「静かに間違った変換をする」ことは起きない。
  - ⚠ **機構 5（属性アクセスへの介入）だけはメタ関数でも代替できない** —
    言語側の計算フィールドが要る（`comptime_metafn_design.md` D33）。
- **参照**: [python_converter_coverage.md](../implementation_plans/python_converter_coverage.md)

# 4. 言語機能の予定（番号なし・[CLAUDE.md](../CLAUDE.md) 由来）

⚠ **タスク番号が付いていない**。着手するなら**まず番号を付けて残タスク表へ載せる**こと。

## (1) ネイティブコンパイルの拡張

- **内容**: `--compile` で**クロージャ・ジェネレータ・`block_return` / `loop_yield`** を
  含む関数もネイティブ化できるようにする。現状これらは**適格判定で落ちて解釈実行へ回る**。
- **前提**: なし（ただし規模が大きい）。
- **留意点**:
  - ⚠ 適格判定は `partial_compiler/llvm_codegen/mod.rs` の `stmt_eligible` / `expr_eligible`。
    ここは `_ =>` が「**ネイティブ非対象**」＝**安全な劣化**なので、
    強制化（#84/#86/#87 の類）はしていない。**広げるときは 1 形ずつ**。
  - ⚠⚠ **ネイティブ codegen を触ったら主検査は `dump_native_ir.ps1` の IR byte-identical**。
  - ⚠ 入れ子 `gen` は **VM 側も未対応**（`decl-prepass:GenDef` で bail）。
    ネイティブ化より先に**VM の対応を決める**ほうが筋が通る。
- **参照**: skill `partial-compile`（適格性ルールと codegen 実装）。

## (2) async の拡張

- **内容**: ネイティブコンパイル済み関数の中の `async` ブロック／
  **明示的な `Mutex` 相当のプリミティブによる共有可変状態**。
- **前提**: なし。
- **留意点**:
  - ⚠⚠ **現在の async は share-nothing が設計判断（D5）**。submit 時に**ディープクローン**する。
    共有可変を入れるなら**明示プリミティブに限る**（暗黙の共有へ倒さない）。
  - ⚠⚠ **`deep_clone` で `Rc` を共有してはいけない**（非アトミック参照カウント。
    不変条件テスト 3 本が固定している）。⚠ **async の実地ストレスでは検出できない**（競合窓が狭い）ので
    **決定的な検査を別に置く**こと。
  - ⚠ **worker スレッドは `Interpreter::new()` を作る**ので、親の設定を引き継がない。
    新しい状態を足したら**渡し忘れがゲートの穴になる**（実際に開いていた）。
- **参照**: プラン D5（区切り線の下の §3.5）／skill `vm-pitfalls` §2。

## (3) 書式指定（f-string の `{x:.2f}` 相当）

- **内容**: **Arrow に「値を書式付きで文字列化する」構文・組込が無い**。
  そのため `import[py]` の f-string 変換（python_converter 項目 19）で
  **`format_spec` 付きだけが明示エラー**になっている:
  - `f"{x:.2f}"`（精度）・`f"{x:>10}"`（寄せ・幅）・`f"{n:,}"`（桁区切り）・
    `f"{n:04d}"`（ゼロ埋め）・`f"{n:x}"`（基数）など **Python の書式指定ミニ言語全般**。
  - `f"{x!a}"`（ascii 変換）も相当する組込が無いので同じく明示エラー。
    ⚠ `!s` → `str()`、`!r` → `repr()` は**対応済み**（どちらも Arrow に組込がある）。
- **前提**: なし。ただし**言語仕様の決定が先**。少なくとも 2 通りある:
  1. 組込関数を足す（`format(value, spec)` / `str.format`）。変換器は
     `f"{x:.2f}"` → `format(x, ".2f")` に脱糖するだけで済む。**変換器側の変更は最小**。
  2. Arrow 自身に書式付き文字列補間の構文を入れる。Arrow の f-string 相当
     （`desugar_fstring`、`src/parser/exprs.rs`）は**現在 `str()` 呼び出しへ脱糖するだけ**なので、
     こちらを選ぶならその脱糖も一緒に設計し直すことになる。
- **留意点**:
  - ⚠ **Python の書式指定ミニ言語は広い**（`[[fill]align][sign][#][0][width][,][.prec][type]`）。
    「全部やる」と決める前に、**どこまでを仕様にするか**を先に決めること。
    部分実装のまま通すと「一部の書式だけ黙って違う結果になる」形になり、最悪。
  - ⚠ 現状は**明示エラー**なので**黙っては壊れていない**。急ぐ理由は
    「f-string を使う実在の Python モジュールが `format_spec` を 1 箇所でも含むと
    **import 全体が落ちる**」という**モジュール単位変換**の性質のほうにある。
  - ⚠ 実装したら `python_converter_coverage.md` の項目 19 の「未対応」記述も**同時に**直すこと。
- **参照**: [python_converter_coverage.md](../implementation_plans/python_converter_coverage.md) 項目 19 ／
  例題 [`examples/interop/py_fstring_error.ar`](../examples/interop/py_fstring_error.ar)
  （エラーになる形を固定してある）／`desugar_fstring`（`src/parser/exprs.rs`）。

## (4) 辞書内包 `{k: v for ...}` とジェネレータ式

内包表記（`[elt for x in it if c]` / `{elt for ...}`）は **Arrow ネイティブ構文・`import[py]` の
両方で対応済み**（`for` 式 + `loop_yield` に脱糖。脱糖器は `ast::build_list_comprehension` の 1 箇所）。
残った 2 形は**どちらも明示エラー**にしてある。

### (4-a) 辞書内包 `{k: v for k in ks}`

- **内容**: 内包表記は「`for` 式 + `loop_yield`」に脱糖する設計で、`for` 式が作れるのは
  **リスト**だけ。セット内包は結果を `set(...)` に通せば済むが、辞書には
  **「ペアのリストから dict を作る」手段が無い**（`dict(pairs)` は
  `TypeError: 'dict' object is not callable`）。
- **前提**: **先に `dict()` コンストラクタ**（`dict([(k, v), ...])` / `dict()`）を用意すること。
  それさえあれば脱糖は `dict([(k, v) for ...])` で済み、**内包表記側の変更は最小**。
  ⇒ 順序は「①`dict()` を足す → ②辞書内包を `dict(<リスト内包>)` に脱糖」。
- **留意点**:
  - ⚠ `dict()` は `list` / `set` と違って**キーの重複規則**（後勝ち）を決める必要がある。
  - ⚠⚠ **タプルを dict のキーにすると黙って消える**既知バグ（§5 参照）がある。
    ペアのリストから dict を作る経路はそこに触れるので、**先にこちらを直す**こと。
  - ⚠ 実装したら `examples/collections/comprehension_error.ar` と
    `examples/interop/py_comprehension_error.ar` の①が**通るようになる**ので、
    例題とエラー文言も同時に直すこと。

### (4-b) ジェネレータ式 `(v for v in xs)`

- **内容**: Python のジェネレータ式は**遅延評価**。リスト内包と同じ脱糖にすると**先行評価**になり、
  無限ジェネレータが止まらなくなる／副作用の回数が変わる。**黙って別物にしないため**に明示エラー。
- **前提**: Arrow の `gen` / ジェネレータ（`Stmt::GenDef`・`Value::Generator`）を使った脱糖を設計すること。
  「合成のジェネレータ関数を作ってその呼び出しに置き換える」形になるので、
  **python_converter 項目 26（lambda lifting）と同じ「式から囲みスコープへ定義を注入する」機構
  （INF-B）が前提**になる可能性が高い。
- **留意点**:
  - ⚠ 安易に「リスト内包と同じ」に倒さないこと。**現状の明示エラーのほうが安全**。
  - ⚠ `sum(v for v in xs)` のような**呼び出し引数の裸ジェネレータ式**が実コードでは最頻出。
    先にそこだけリスト内包へ倒す案もあるが、**副作用と無限列で挙動が変わる**ので仕様判断が要る。
- **参照**: 例題 [`examples/interop/py_comprehension_error.ar`](../examples/interop/py_comprehension_error.ar)。

# 5. タスク化していない既知の課題（**起票候補**）

## (z) ⚠ `for` のループ変数を捕捉する入れ子 `fn` が VM に載らない（`VmForceError`）

- **現象**（純 Arrow で再現・2026-09-19 に変換器の項目 26 の作業中に発見）:
  ```text
  fn f(mut xs: list[int]) -> int:
      mut s = 0
      for v in xs:
          fn g() -> int:
              return v          # ← ループ変数を捕捉
          s = s + g()
      return s
  # VmForceError: cannot compile function 'f' to bytecode
  ```
- **切り分け済み**（この 3 つは通る ＝ 落ちるのは**ループ変数の捕捉だけ**）:
  | 形 | 結果 |
  |---|---|
  | `for` 本体・ループ変数**以外**を捕捉 | ✅ 通る |
  | `while` 本体・外側の `mut` を捕捉 | ✅ 通る |
  | ループの外で捕捉 | ✅ 通る |
- **見立て**: B4 で `for` のループ変数を**ブロック内の束縛**にした（規則 2/3）ので、
  VM の自由変数収集がその束縛種別を扱えていない可能性が高い。B7（`local::args` を
  拾っていなかった）と**同じ系統**に見える。
- **意義**: Python の `for v in xs: g = lambda z: z + v` が**そのまま書けない**。
  変換器の項目 26（lambda 持ち上げ）が通る形を広げたぶん、ここが目立つようになった。
- **参照**: [`py_lambda.ar`](../examples/interop/py_lambda.ar) の注記（この形だけ例題に
  入れていない理由）／ [bug_fix.md](bug_fix.md) B4・B7。

## (a) ⚠⚠ 入れ子 `fn` の中に 1 度も書かれていない構文が 10 件（`NESTED-GAP`）

- **意義**: **歴史的な実バグ 5 件のうち 4 件が入れ子 `fn` の文脈で起きた**。
  そこに例題が無い構文が 10 件残っている ＝ **次にバグが出るなら最も確率が高い場所**。
- **現在の 10 件**: `Assign` / `AttrAssign` / `Pass` / `Yield` / `BreakPoint` /
  `Undefined` / `List` / `TraitAccess` / `Cast` / `LocalVar`。
- **やり方**: `../scripts/syntax_cov.ps1`（要 `--features tw_stats`）を走らせて最新の一覧を取り、
  例題を足す。⚠ **足す前に手で叩いて `python -m impl_python` と突き合わせる**
  （#85 ではそこで既存の実装差を 1 件踏んだ）。
- **参照**: 実装ログ #85／プランの検証スクリプト表。

## (b) ⚠⚠ 壊れたまま全ゲートを素通りしている例題が 2 本

- `examples/interop/subdir/sub_module.ar` と `sub_script.ar` が
  **実在しない `tl_math` を import** している（`.tl → .ar` の改名/再編の取り残しと思われる）。
- ⚠⚠ **どのゲートも捕まえていない** — `scan_examples` は**非再帰**でこのディレクトリを見ず、

- **判断が要る**: 直すのか消すのか（例題の意図が読めないため #85 では触っていない）。

## (c) 式位置のインクリメント `++`（`arr[i++]`）

- **文位置（`x++`）なら AST 追加ゼロで通せる**（`CompoundAssign` / `AttrCompoundAssign` へ脱糖。
  パーサ内脱糖の前例は f-string → `str()` 呼び出し）。⇒ 冗長性の課題にならない。
- ⚠⚠ **式位置は別物**。現在 `Expr` に**変数へ書き込む variant は 0 個**で、
  複数の最適化が「**式は概ね純粋**」を前提にしている（`compile_attr_compound_assign` の
  `Swap` 省略など）。**判定は保守的ホワイトリストなので既定は安全側＝今は壊れない**が、
  **採用を決めたらその前提の列挙が先**。
- **参照**: 実装ログ「#84〜#89 …… 結果 ③」。

## (d) `let` 束縛のフィールド代入で Rust と `impl_python` の挙動が違う

- `let bx = Box(0)` として `bx.v += 5` すると **Rust は `cannot assign to immutable field`・
  `impl_python` は通る**。⚠ **クロージャとは無関係**（入れ子 `fn` 無しでも再現）。
- ⚠ **どの例題も書いていない形**なので `compare_python_impl.ps1` にも映っていない。
- **言語設計の決定が先**（どちらが正しいか）。決まったら例題を足して固定する。

## (e) `examples/bench/bench_ab_native.ar` が完走しない

- `compare_bytecode.ps1` と `force_gate.ps1` で**タイムアウト**する。
- ⚠ **この系列の変更とは無関係**と 3 通りで確認済み（同一 exe の負の対照でも同じ／
  過去のバイナリでも 60 秒で終わらない／**180 秒でも終わらない**）。

## (f) ⚠⚠ 関数の中の `block` 退出でリソースが解放されない

- **現象**（純 Arrow で再現・2026-09-19 に変換器の項目 25（`with`）の作業中に発見）:
  最上位の `block` と**関数退出**では `Drop` が走るのに、**関数の中の `block` を
  抜けても走らない**。
  ```text
  fn write_then_read(path: str) -> str:
      block:
          mut f = open(path, FileOpenMode.rewrite)
          f.write("hi")
      # ← ここで閉じてほしいが閉じていない
      mut g = open(path, FileOpenMode.read)
      return g.read()     # 空に見える
  ```
- ⚠ **明示クローズもできない** — `FileObject` に `close()` メソッドが無い。
- **意義**: 項目 25 の `with` は `block` へ脱糖するので、**`with` で書いた直後に
  同じ関数の中で読み直す**という Python で当たり前の形が通らない。
  coverage 🟡「with 文」の「参照カウント基準の遅延破棄は実質無視できる」という
  見立ての**反例**。
- **判断が要る**: スコープ退出で解放するのか、`close()` を生やすのか、両方か。
- **参照**: [PYTHON_CONVERTER_LOG.md](PYTHON_CONVERTER_LOG.md) §5.2 #10。

## (g) `with` が他モジュール由来のコンテキストマネージャを検出できない

- 項目 25 の実装は「`__enter__` / `__exit__` を**同じモジュールで定義しているクラス**」
  しか判定できない。`import` してきた CM は**検出できない**ので、
  `__exit__` の副作用（ロック解放・commit / rollback）が黙って落ちる。
- **原因**: `hasattr` 相当の組込みが無く、**実行時ガードを組めない**。
- ⚠ **組込みを足すのは Arrow 側への露出**なので、方針が決まるまで動かさない
  （`list()` / `dict()` を誤って露出させた前例がある）。
- **参照**: [PYTHON_CONVERTER_LOG.md](PYTHON_CONVERTER_LOG.md) §5.3 #3。

## (h) `import[py]` の循環 import が CPython と違う（明示エラー）

- CPython は**部分初期化のモジュール**を渡して通すが、Arrow は
  `circular import detected` で止める。
- **原因**: Arrow の import は**パース時に AST を確定させてから**型検査する形なので、
  「途中の姿」を持てない。⇒ 相互 import を含む実在の Python パッケージが読めない。
- **回避**: 片方を関数内 import にする（が、それは (i) で効かない）／共通部分を
  3 つ目のモジュールへ切り出す。
- **参照**: 例題 [`py_import_stdlib_error.ar`](../examples/interop/py_import_stdlib_error.ar) の ②、
  [PYTHON_CONVERTER_LOG.md](PYTHON_CONVERTER_LOG.md) §5.5。

## (i) `import[py]` は Python の**関数内 import** を充填しない

- 項目 27 の再帰ロードが走査するのは**モジュール本体の直下だけ**。関数の中に書かれた
  `import` は文の位置を保ったまま残り、`body` が空のままなので**実行時に未定義**になる。
- ⚠ Python の関数内 import は**遅延読み込み・循環回避の意図**で書かれることが多い。
  「本体直下と同じく事前に読む」と意図を壊すので、**設計判断が先**。
- **参照**: [PYTHON_CONVERTER_LOG.md](PYTHON_CONVERTER_LOG.md) §5.5。

## (j) ⚠ `compare_wasm_frontend.ps1` が wasm を再ビルドしない

- 存在確認しかしないので、**古い `.wasm` のまま緑になる**。
  lexer / parser / type_check を触ったら
  `cd crates/arrow-frontend && cargo build --release --target wasm32-unknown-unknown` を
  明示的に回す必要がある。
- ⚠⚠ **この系列の作業中だけで 3 回踏んだ**（C3・辞書展開・enumerate/zip）。
  「緑のゲートが嘘をつく」形なので、スクリプト側で再ビルドするか、
  ソースより古い `.wasm` を検出して落とすのが筋。
- **参照**: `vm-pitfalls` §3、
  [PYTHON_CONVERTER_LOG.md](PYTHON_CONVERTER_LOG.md) §5.2 #4。

## (k) ⚠⚠ `cargo test`（debug）がビルド不能になっても**どのゲートも気づかない**

- **2 つの別の穴が重なっている。**
  1. テストは**別ビルド** ⇒ AST を変えたときの `src/frontend_tests/` の取りこぼしを
     `cargo build` では検出できない（`ForExpr { target }` → `targets` で踏んだ）。
  2. ⚠⚠ **`cfg(debug_assertions)` の強制点は release に存在しない** ⇒
     `vm/compiler/mod.rs` の `storage_operands`（op の網羅 `match`）は
     **release ビルドでは丸ごと消える**。`scripts/*.ps1` のゲートは全部
     `target/release` を見るので、**op を足し忘れても全ゲートが緑**になる。
- **実績 2 回**:
  | いつ | 何 | 気づくまで |
  |---|---|---|
  | 2026-09-08 `15aa677` | `Op::CoerceFloat` | **73 コミット**（タスク 9.8） |
  | 2026-09-19 `c06254f` / `8c61d07` | `Op::SeqExtend` / `SeqFinish` / `DictMerge` | **8 コミット**（`361994a` で修正） |
- ⭐ **2 回目は「`cargo test` を回す」という運用では防げなかった。**
  実際に走らせたのは **`cargo test --release`** で、784 passed と出ていた。
  **`--release` では強制点そのものがコンパイルされない**ので、網になっていない。
  ⇒ 運用に落とすなら「`cargo test` を回す」ではなく
  **「`cargo test`（`--release` を付けない）を回す」**と書かないと意味が無い。
- **直し方の候補**（どれも未実施・要判断）:
  - ゲートの前段に **`cargo test --no-run`（debug）** を置く。いちばん安い。
  - `storage_operands` の `cfg(debug_assertions)` を外し、
    `#[cfg(any(test, debug_assertions))]` か、素の関数にして release でも型検査させる
    （呼び出し側だけ `cfg` で切る）。⚠ release バイナリへの影響を測ってから。
  - `force_gate.ps1` / `scan_examples.ps1` に **debug バイナリでの 1 周**を足す
    （`debug_assert!` のスロット範囲検査が初めて実際に走る）。

  `src/vm/compiler/mod.rs` の `storage_operands` の doc（この罠を警告している本体）／
  skill `vm-pitfalls`。
