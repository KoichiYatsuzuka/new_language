## #19 — py 組み込みスタブの整備（`time` / `math`）

- **意義**: 型検査の推論が `Unresolved` に落ちる**最大の残存要因**。
  `time.time()` のような **C 実装の py 組み込みモジュール**は `.py` ソースが無く
  スタブを抽出できないため、**型検査の推論規則ではこれ以上詰められない**と結論が出ている。
  ⇒ 潰し方は「推論を賢くする」ではなく「**スタブを置く**」方向（#17-b と同じ）。
- **効果の見込み**: `Unresolved` が減ると binop / call の型特化が乗る。
  ⚠ **数値は測っていない**。着手時は `AR_ANNOT_DIFF=1`（`AnnotUnresolvedSrc`）で
  **現在の発生源内訳を取り直してから**決めること。
- **前提**: なし。
- **手法**: 同梱 `.pyi` を用意し、`python_search_dirs()` に置き場を追加する。
- **留意点**:
  - ⚠ **グローバル名を占める登録は慎重に。** 組み込み関数の型を型検査のグローバルへ入れると
    `let <name> = ...` が「already declared」の**静的エラーになる**。過去に `len` / `repr` は
    この理由で**意図的に外した**（特化件数の伸び +1 に対して既存コードを壊す割に合わない）。
    `range` だけ登録されているのはループ形の頻度が圧倒的で変数名に使われないため。
  - ⚠ スタブの探索方針は `ar_config.json` 側と**一貫させる**（#72/#74 で読み手を 1 本化した）。
- **参照**: skill `importation`（`import[py]` の実装）／skill `type-checking`（推論規則）／
  実装ログ #16 の「残る miss の主因」。

## #17-b — JS スタブの型付け

- **意義**: **JS は `.ars` に型が書かれて初めて FFI 境界検査が効く**。現状の `.ars` は型を持たず
  **実質無検査**。FFI 境界検査の設計は「**スタブが宣言した型を検査の根拠にする**」向きなので、
  スタブが整うほど強くなる（従来の `CheckBefore` とは逆向きの性質）。
- **前提**: なし。
- **手法**: 既定は `Any`。`.d.ts` があればそれを読んで `.ars` を生成する。
- **留意点**:
  - ⚠ **既定を `Any` にすること**（型が無い状態を「検査しない」に倒す）。
    厳しくすると既存の JS 連携が一斉に落ちる。
  - ⚠ 生成した `.ars` は**キャッシュの鮮度**に注意（`import[cs-dll]` の `.ars` と同じ扱い）。
- **参照**: skill `importation`（`import[js-proc]`）／実装ログ「この機構でも救えない範囲（→ #17 へ昇格）」。

## #17-a — C/C++ の `void*` に専用型を導入

- **意義**: **C/C++ の `void*` は Arrow の `int` に落ちる**。型タグは「int である」以上を語らないので、
  **動的検査を入れても静的型と同じことしか言えない**。⇒ 不透明ハンドル型を導入して
  **int との相互代入を静的に禁止**するのが唯一の前進。
- **前提**: なし。
- **手法**: 不透明ハンドル型（opaque handle）を型検査へ足し、`int` との暗黙変換を禁止する。
- **留意点**:
  - ⚠ **話題は C/C++ 相互運用だが、変更は静的型検査だけ**（実行時表現は変えない）。
    実行時ディスパッチに触ると別タスクになる。
  - ⚠ **既存コードが `void*` を int として扱っている箇所**が壊れる。
    静的エラーを増やす変更なので、**例題とテストの落ち方を先に測る**こと。
  - ⚠ ネイティブ ABI 側の表現（`InstanceData` の raw ブロック等）と整合させる。
- **参照**: skill `c-abi-interop`（C ABI 型注釈と raw レイアウトの設計仕様）／skill `type-checking`。

## #89 — メタプログラミングの前提（`Value → AST` ＋ AST→実行の入口）

- **意義**: 「実行時に AST を組み立てて実行する」ための**足りない 2 つ**を埋める。
  #84〜#85 の評価で、**メタプロが「expr を 1 個足す」で済まない理由は AST 側ではなく
  `Value↔AST` 境界とパイプライン入口にある**と判明している。
- **前提**: ← #84（済）・#85（済）＋ ⚠ **消費者の出現**（現在**居ない**）。
  判定基準は「**消費者が居るか**」（#11 R2-c / #14 / #15b を保留にしたのと同じ基準）。
- **今ある追い風**（着手時に活かす）:
  - **AST は既に第一級の値** — `src/interpreter/ast_value.rs`（Stmt 40 / Expr 29 が exhaustive）。
  - **実行時に AST を作って実行するのは `templates.rs` が実証済み**（型引数キーの Chunk メモ化）。
  - **合成 AST は `node_id: 0` / `Resolution::Unresolved` でも正しく動く**（＝「遅いが動く」が既定）。
  - **パイプラインが `&mut Vec<Stmt>` の独立パス**なので、展開パスは parse と type_check の間に挟める。
- **足りないもの**:
  1. **`Value → AST` の逆変換が無い**（`ast_value.rs` は一方向のみ）。
  2. **AST→実行の入口が無い** — `vm/compiler/entry.rs` の `compile_debug` は
     `Stmt::Expr` / `Stmt::Let` の **2 形だけ**で `_ => return None`。
- **留意点**:
  - ⚠⚠ **`Value` は動的なので match で守れない。** 逆変換を書くと、#59/#81/#84 が塞いだ
    「ドリフトを強制で止める」網の**外側**に大きな面ができる。**#84・#85 の強制点が
    先に要る**と判断したのはこのため。
  - ⚠ 展開パスを足すなら**配線は 1 箇所**（#88 の `resolve_and_annotate`）に足す。
- **参照**: 実装ログ「#84〜#89 …… 結果 ③」（メタプロの追い風/向かい風の全リスト）。

## #14 — モジュール動的リンク（ネイティブ経路の安全な動的リンク）

- **意義**: 現状は `try_load_native_module` が**関数ごとに `GetProcAddress`**（`{fn_name}_tl` シンボル）を
  引いている。これを**モジュールにつき 1 回**（単一ディスクリプタシンボル ＋ ABI ハッシュ照合）へ改める。
  シンボル数が増えるほど効き、**大規模（~5000 sym）で ~10ms → <1ms** の見積もり。
- **前提**: ← ⚠⚠ **「モジュール間ネイティブ直リンク」の導入（未実装・未計画）**。
  現状はモジュールが互いをネイティブに直接呼ばないので、**この最適化の消費者が居ない**。
  ⇒ **まず「モジュール間直リンクをやるか」を決めるのが先**。
- **留意点**:
  - ⚠ `.arc` フォーマット（`partial_compiler/module_compiler.rs` の `write_tlc_native`, v1）の**拡張**になる。
    形式が変わるとブランチ間で `.arc` の互換が切れる（A/B 計測時は**測る側のバイナリで `--compile` し直す**）。
  - ⚠ **循環 import**（A⇄B）は「全シンボル宣言（index 採番）→ 本体解決」の 2 フェーズで解く方針が
    決まっている（§9-5 の未決事項もこれに従属）。
- **参照**: **[BYTECODE_VM_PLAN.md](BYTECODE_VM_PLAN.md) §6**（区切り線の下）にディスクリプタ構造・
  ロード手順・コスト概算の**完全仕様**がある。⇒ **着手時はそこから読む**。skill `partial-compile`。

## (1) ネイティブコンパイルの拡張

- **内容**: `--compile` で**クロージャ・ジェネレータ・`block_return` / `loop_yield`** を
  含む関数もネイティブ化できるようにする。現状これらは**適格判定で落ちて解釈実行へ回る**。
- **前提**: なし（ただし規模が大きい）。
- **留意点**:
  - ⚠ 適格判定は `partial_compiler/llvm_codegen/mod.rs` の `stmt_eligible` / `expr_eligible`。
    ここは `_ =>` が「**ネイティブ非対象**」＝**安全な劣化**なので、
    強制化（#84/#86/#87 の類）はしていない。**広げるときは 1 形ずつ**。
  - ⚠⚠ **ネイティブ codegen を触ったら主検査は `dump_native_ir.ps1` の IR byte-identical**。
  - ⚠ 入れ子 `gen` は **VM 側も未対応**（`decl-prepass:GenDef` で bail）。
    ネイティブ化より先に**VM の対応を決める**ほうが筋が通る。
- **参照**: skill `partial-compile`（適格性ルールと codegen 実装）。

## (2) async の拡張

- **内容**: ネイティブコンパイル済み関数の中の `async` ブロック／
  **明示的な `Mutex` 相当のプリミティブによる共有可変状態**。
- **前提**: なし。
- **留意点**:
  - ⚠⚠ **現在の async は share-nothing が設計判断（D5）**。submit 時に**ディープクローン**する。
    共有可変を入れるなら**明示プリミティブに限る**（暗黙の共有へ倒さない）。
  - ⚠⚠ **`deep_clone` で `Rc` を共有してはいけない**（非アトミック参照カウント。
    不変条件テスト 3 本が固定している）。⚠ **async の実地ストレスでは検出できない**（競合窓が狭い）ので
    **決定的な検査を別に置く**こと。
  - ⚠ **worker スレッドは `Interpreter::new()` を作る**ので、親の設定を引き継がない。
    新しい状態を足したら**渡し忘れがゲートの穴になる**（実際に開いていた）。
- **参照**: プラン D5（区切り線の下の §3.5）／skill `vm-pitfalls` §2。

# 5. タスク化していない既知の課題（**起票候補**）

## (a) ⚠⚠ 入れ子 `fn` の中に 1 度も書かれていない構文が 10 件（`NESTED-GAP`）

- **意義**: **歴史的な実バグ 5 件のうち 4 件が入れ子 `fn` の文脈で起きた**。
  そこに例題が無い構文が 10 件残っている ＝ **次にバグが出るなら最も確率が高い場所**。
- **現在の 10 件**: `Assign` / `AttrAssign` / `Pass` / `Yield` / `BreakPoint` /
  `Undefined` / `List` / `TraitAccess` / `Cast` / `LocalVar`。
- **やり方**: `../scripts/syntax_cov.ps1`（要 `--features tw_stats`）を走らせて最新の一覧を取り、
  例題を足す。⚠ **足す前に手で叩いて `python -m impl_python` と突き合わせる**
  （#85 ではそこで既存の実装差を 1 件踏んだ）。
- **参照**: 実装ログ #85／プランの検証スクリプト表。

## (b) ⚠⚠ 壊れたまま全ゲートを素通りしている例題が 2 本

- `examples/interop/subdir/sub_module.ar` と `sub_script.ar` が
  **実在しない `tl_math` を import** している（`.tl → .ar` の改名/再編の取り残しと思われる）。
- ⚠⚠ **どのゲートも捕まえていない** — `scan_examples` は**非再帰**でこのディレクトリを見ず、
  `force_gate` は `VmForceError` しか見ないので `ParseError` は素通りする。
- **判断が要る**: 直すのか消すのか（例題の意図が読めないため #85 では触っていない）。

## (c) 式位置のインクリメント `++`（`arr[i++]`）

- **文位置（`x++`）なら AST 追加ゼロで通せる**（`CompoundAssign` / `AttrCompoundAssign` へ脱糖。
  パーサ内脱糖の前例は f-string → `str()` 呼び出し）。⇒ 冗長性の課題にならない。
- ⚠⚠ **式位置は別物**。現在 `Expr` に**変数へ書き込む variant は 0 個**で、
  複数の最適化が「**式は概ね純粋**」を前提にしている（`compile_attr_compound_assign` の
  `Swap` 省略など）。**判定は保守的ホワイトリストなので既定は安全側＝今は壊れない**が、
  **採用を決めたらその前提の列挙が先**。
- **参照**: 実装ログ「#84〜#89 …… 結果 ③」。

## (d) `let` 束縛のフィールド代入で Rust と `impl_python` の挙動が違う

- `let bx = Box(0)` として `bx.v += 5` すると **Rust は `cannot assign to immutable field`・
  `impl_python` は通る**。⚠ **クロージャとは無関係**（入れ子 `fn` 無しでも再現）。
- ⚠ **どの例題も書いていない形**なので `compare_python_impl.ps1` にも映っていない。
- **言語設計の決定が先**（どちらが正しいか）。決まったら例題を足して固定する。

## (e) `examples/bench/bench_ab_native.ar` が完走しない

- `compare_bytecode.ps1` と `force_gate.ps1` で**タイムアウト**する。
- ⚠ **この系列の変更とは無関係**と 3 通りで確認済み（同一 exe の負の対照でも同じ／
  過去のバイナリでも 60 秒で終わらない／**180 秒でも終わらない**）。
  `examples/bench/bench_ab_native_module.arc` の鮮度に依存する形。
- ⇒ **`force_gate` の「0 件」はこの 1 本を見ていない**ことを含めて読むこと。
