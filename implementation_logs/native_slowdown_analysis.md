# コンパイルすると VM より遅くなる操作 — 測定方法・測定結果・要因

- 調査: 2026-10-28。対象は `a7d5152`（コードは `e8b6fc5` = native_object_access_plan.md のフェーズ 11・12 完了時点）・
  release ビルド・Ryzen 5 5600X / Windows 11
- 関連: [native_object_access_plan.md](native_object_access_plan.md)（§0.4〜§0.8 の速度の記録・各フェーズの対策）、
  [known_problems.md](../implementation_logs/known_problems.md)（対応しないと決めた問題）
- 状態: 調査のまとめ。**対策は未起票**（候補は §5。着手は利用者の判断）

## 1. 結論

- **区間（まとまった処理）で、コンパイルして遅くなるものは無い。** ベンチの 6 区間すべてでコンパイル済みが VM と同じか速い
  （1.03〜2.70x）。最大のメモリも同じ。
- **1 操作の単位では、5 つの操作がコンパイルすると遅い**: 文字列の連結（1.74x）・入れ子の書き込み（1.50x）・`Vec3` の生成と
  束縛（1.24x）・`Body` の生成（1.15x）・入れ子の読み出し（1.08x）。
- いちばん大きい要因は、**ループの周ごとの巻き戻しが、生きている値があると毎周 `Vec` を確保すること**（要因 11・1 周 30〜43 ns）。
  これは挙動を変えずに直せる。残り（要因 12〜15）は、コンパイル済みコードが値をハンドル（アリーナの番号）で持ち、操作のたびに
  コールバックでインタープリタへ渡す仕組みの費用で、1 回あたり 15〜55 ns。

## 2. 測定方法

すべて `scripts/` の PowerShell スクリプトで、例題はリポジトリの外（`%TEMP%`）へ写して走らせる。コンパイル済みのモードは
**測る exe 自身で `--compile`** する（`.arc` は作った exe の生成コードを埋め込むので、別の exe の `.arc` を読むと比べられない）。

### 2.1 ベンチ（区間・1 操作の単価）

[examples/bench/speed_modes/](../examples/bench/speed_modes/) を [speed_modes.ps1](../scripts/speed_modes.ps1) で走らせる。

```powershell
./scripts/speed_modes.ps1                          # 区間（bench.ar）を 3 モード（VM / コンパイル済み / C++ の DLL）で
./scripts/speed_modes.ps1 -Micro                   # 1 操作の単価（micro.ar・ns）
./scripts/speed_modes.ps1 -Exe <a.exe> -B <b.exe>  # 2 つの exe をモードごとに A/B
```

| 区間 | 内容 |
|---|---|
| `k1_step` | 数値のメソッド（`Vec3` / `Body` の物体シミュレーション 256 体） |
| `k2_energy` | `list[Body]` の反復と `let self` のメソッドの連鎖 |
| `k3_record` | `list[float]` への追加と集計 |
| `k4_labels` | 文字列の連結・`int` → `str` |
| `k5_spawn` | 生成 |
| `k6_boundary` | インタープリタからコンパイル済みのメソッドを呼ぶ境界 |
| `process_wall` / `peak_mb` | 起動を含むプロセス全体の時間 / 最大のワーキングセット |

1 操作の単価は `(t(操作のループ) − t(空のループ)) / n`。7 回の中央値（1 周目は捨てる）・scale 5。区間の結果（`CHECK`）が
モード間・exe 間で一致することも確かめる（計算をしていないだけで速く見えるのを見逃さない）。

[speed_milestones.ps1](../scripts/speed_milestones.ps1) が計画の各時点の commit を worktree で作り、`speed_modes.ps1 -Exes` で
全部の exe を交互に測って中央値を横に並べる（native_object_access_plan.md §0.7）。

### 2.3 操作の分解

[native_slowdown.ps1](../scripts/native_slowdown.ps1) が [slowdown.ar](../examples/bench/speed_modes/slowdown.ar) /
[slowdown_core.ar](../examples/bench/speed_modes/slowdown_core.ar) を VM とコンパイル済みで交互に走らせ、操作ごとの単価と差を出す。
**束縛する形としない形を並べ**、差から束縛の費用を読む。

```powershell
./scripts/native_slowdown.ps1                      # VM / コンパイル済み / 差
./scripts/native_slowdown.ps1 -B <実験用の exe>     # 実験用の exe のコンパイル済みの列を足す
```

| カーネル | 操作（ループの中） |
|---|---|

| `str_add_vars` / `str_add_discard` | `let s = a + b` / `a + b`（束縛しない） |

| `new_vec` / `new_vec_discard` | `let v = Vec3(1.0, 2.0, 3.0)` / `Vec3(1.0, 2.0, 3.0)` |
| `field_write` / `nested_write` / `nested_read` | `b.mass = 1.0` / `b.pos.x = 1.0` / `acc += b.pos.x` |
| `append_float` / `append_str` | `xs.append(1.0)` / `xs.append(s)` |
| `len_callback` | `k = len(xs)`（何も積まないコールバックの費用の目安） |

### 2.4 実験用の exe

要因を確かめるときは、**コールバックか生成コードの 1 か所だけを変えた exe** を作り、`speed_modes.ps1 -B` か
`native_slowdown.ps1 -B` で今の exe と比べる（変更はリポジトリに残さない）。今回の要因に使った実験:

| 実験 | 変えた所 | 分かったこと |
|---|---|---|
| 巻き戻しで `Vec` を作らない | `ar_compact_many`: 残す値が 1 つのとき、`Vec` を作らずに写して縮めて積み直す | 要因 11 の大きさ |
| 束縛の仕事を省く | `ar_bind_value`: 作りたての値の印があれば、写して積み直すだけ（共有の判定・フリーズをしない） | 要因 12 の内訳（コールバックそのもの / 束縛の仕事） |
| 束縛ごと省く | `ar_bind_value`: 作りたての値の印があればハンドルをそのまま返す（上限の目安。挙動は誤り） | 同上 |
| `float` の結果を箱に詰めない | ガード付きのメソッド呼び出しの結果を `double` で合流する | known_problems.md #1 |

### 2.5 注意

- **ノイズの幅は同じセッションで測る**: 同じ exe 同士（`-Exe X -B X`）が対照。今回のセッションの対照は、1 操作の単価で
  0.986〜1.017x、別のセッションでは 0.891〜1.064x まで揺れた。生成のカーネルは実行の間で ±30 ns ほど揺れる。
- release の exe を測る（`cargo build --release`）。
- 初期（`326e112`）のコンパイル済みの数字は、一部比べられない: 当時の生成コードは VM と違う（誤った）ことをしていた
  （`let` の受け手のフィールドを入口で 1 回だけ読む・`mut` の値を `let self` で受けても複製しない）ので、その分の仕事をしていない。

## 4. 要因

### 要因 11: ループの周の巻き戻しが、毎周 `Vec` を確保する（いちばん大きい）

- **何が起きるか**: ループの本体でハンドル（オブジェクト・文字列など）を変数に書くと（`let s = ...`・`let v = ...`）、周の終わりに
  生成コード（`gen_loop_body`・native_object_access_plan.md 9-1）が `ar_compact_many` を呼ぶ。`ar_compact_many` は残す値を
  `Vec<Value>` に写してからアリーナを保存点まで縮め、積み直す。この `Vec` の確保と解放が周ごとに起きる。
- **証拠**: §3.3 の B の列。残す値が 1 つのとき `Vec` を作らないだけで、`str_lit` 73.0 → 29.7 ns・`str_add_vars` 227.7 → 184.8 ns・
  `str_concat` 262.8 → 220.5 ns・`new_vec` 558.8 → 502.6 ns（1 周 30〜56 ns）。束縛しない形（`*_discard`）・残す値が無いループ
  （`nested_write` など）は変わらない。
- **読んで分かったこと**: 保存点より下のハンドル（ループの前からある値）も毎周積み直している。動かす必要は無い。
- VM は値を自分の欄に置くだけで、巻き戻しに当たる仕事が無い。

### 要因 12: `let` / `mut` の束縛のコールバック

- **何が起きるか**: 宣言の束縛は `ar_bind_value`（field 56）を呼ぶ: 値をアリーナから写し、`bind_copy`（共有の判定・フリーズ）を
  して積み直す。VM の束縛（`STORE_LOCAL_FREEZE_INST`）は同じ `bind_copy` を値を動かさずに呼ぶ。
- **証拠**: `str_add_vars` と `str_add_discard` の差は、巻き戻しの分（要因 11）を除いても約 40〜55 ns（VM では 3 ns）。§3.4 で、
  文字列の束縛ではコールバックそのもの（写す・積み直す）が約 20 ns、束縛の仕事が約 20 ns。生成した値の束縛では、コールバック
  そのものの費用は測れないほど小さく、束縛の仕事（両モード共通の `bind_copy`・`__freeze__` を名前で引く）が主。
- 12-2（値を作るコールバックで束縛まで行う）は、束ねて省けるのが文字列の約 20 ns だけなので見送った。

### 要因 13: 生成の道

- **何が起きるか**: `Vec3(1.0, 2.0, 3.0)` は、引数の `float` 3 つをそれぞれ `make_float` でアリーナに積み、`construct_ic`
  （field 70）が引数をアリーナから写して評価済みの引数の `Vec` を作り、`instantiate_evaled` を呼んで結果を積む。VM は値を
  スタックから渡す。
- **証拠**: 束縛しない生成（`new_vec_discard`）でも +22〜71 ns（実行の間で揺れる）。

### 要因 14: 入れ子の書き込み

- **何が起きるか**: `b.pos.x = 1.0` は 12-3 から 1 回のコールバック（`assign_path_ic`・field 74）になったが、その中で根をアリーナから
  写し、段の表を読み、途中の値を（参照数を上げて）読み、最後に `attr_assign_ic` で書く。VM の途中の読み出しはスタックの上で済み、
  `b.pos.x = 1.0` は `b.mass = 1.0` と同じ費用。
- **証拠**: `nested_write` +18 ns（`field_write` は +3 ns）。12-3 の前は +25 ns。

### 要因 15: 文字列のリテラル

- **何が起きるか**: 11-2 からリテラルは箇所ごとに 1 回だけ作るが、評価のたびに `make_str_ic`（field 72）を呼んでアリーナに積む。
  VM は定数表の値を参照数の加算で積むだけ。
- **証拠**: `str_lit` の差は、巻き戻しの分を除いて +15 ns（§3.3 の B）。

### そのほか（記録済み）

- **ガード付きのメソッド呼び出しの `float` の結果の箱詰め**: 注釈で受け手を決めた呼び出しの結果をハンドルで合流するので、結果を
  使う演算が型の無い道になる（k2 で 1.06x 分）。対応しない（[known_problems.md](../implementation_logs/known_problems.md) #1）。
- **`let self` / `mut self` のメソッドとフィールドの書き込みの退行**: フェーズ 9・10 完了 → 現在で 3〜6%（両モード）。同じ exe 同士の
  対照より大きく、再現する。原因は未特定（native_object_access_plan.md §0.7）。
