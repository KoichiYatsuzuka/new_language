# 落とし穴（既知） — 解決層 / バイトコード VM

Phase R（AST 解決層）・Phase V（バイトコード VM）の実装で**実際に踏んだ**罠。
各項の `#N` は [IMPLEMENTATION_LOG.md](../../../IMPLEMENTATION_LOG.md) のタスク番号。
計画・現在地は [BYTECODE_VM_PLAN.md](../../../BYTECODE_VM_PLAN.md)。

> 共通する形は **「テストは通ってしまう」「ゲートは緑のまま」**。
> ここに並ぶのは *壊れ方が見えない* 失敗ばかりで、見えるバグはそもそも載っていない。

---

## 1. 計測と A/B ベンチ

- **⚠⚠ 実行命令の割合は「時間の割合」ではない**（#46）。`Jump` は実行命令の **12%** だが
  時間では **0.3%**（空ループで命令数 -20% にしても **1.003x**）。**命令には値段の差がある**。
  ⇒ 命令数の内訳は **当たりを付ける** のには使えるが、**速度の予測には使えない**。
  安い命令ではなく **`exec_op` 1 回あたりのコスト** か **高い命令**（`Call`/`GetAttr`/`Store*`）を狙う。
- **⚠⚠ 最適化は「何個あるか」ではなく「何回動くか」で決める**（#24）。逆アセンブルの静的頻度で
  1 位だった `POP; RETURN_NIL`（6.68%）は **最上位文ごとに 1 回** 動くだけで、1.5 億命令の
  ベンチには現れない。**到達不能コードの除去は原理的に速度へ効かない**（実行されないものを消すため）。
  ⇒ 判断の前に **ディスパッチループで実行 op を数える**（一時計測でよい。#24 では入れて測って撤去）。
- **⚠ ノイズ床のプローブは「変更と同規模」で測る**（#27）。opcode を足す規模の摂動は
  **1 命令も実行しなくても** ベンチを 0.88〜0.94x 動かす（小関数 1 本のプローブは規模不足）。
  ⇒ この規模の変更は VM 支配ベンチを ±5% 揺らす。**数 % で良し悪しを決めない**。
- **A/B は必ず交互実行**（A,B,A,B…）。A を N 回 → B を N 回だとサーマルドリフトで
  実在しない退行が見える。
- **⚠⚠ 「exec が N 倍」は「全体が N 倍」ではない**（#50）。例題 1 本の中央値では
  **exec は全体の 14%**（0.46ms / 3.40ms）しかなく、**exec を無限に速くしても端点は 1.59x**。
  残りはプロセス費用 1.5ms・`interp_init` 0.32・`type_check` 0.18・`parse` 0.17。
  ⇒ 速度の話をする前に **[prof_dist.ps1](../../../prof_dist.ps1) で段別分布を取る**。
- **⚠⚠ 1 回目の実行はコールドリードを踏む — プロファイラだけでなく素のベンチもである**（#50 → #70）。
  #50 では `startup` が **0.1ms → 10ms** に化け、最初の集計が丸ごと汚染された。
  #70 では **`cargo build` 直後の初回**の `bottleneck_bench.ar` が `fn call` を **0.405µs** と出し
  （2 回目以降は **0.123〜0.135µs**＝記録どおり）、**存在しない 3x の退行を報告してしまった**。
  ⇒ **必ず 2 回以上走らせて 1 本目を捨てる**。⚠ 「前回測定から時間が空いた値」との比較でも
  同じ誤りが起きる（#21-b）。**退行を主張する前に、同じセッションで A/B を取り直すこと。**
- **⚠⚠ プロファイラの「もっともらしい分布」ほど負の対照で裏を取る**（#50）。VM フレームが
  返った後にサンプラーの「今の op」を戻し忘れ、**`event_handler.ar` の 1 秒の待ちが丸ごと
  `ReturnNil` に化けて「`ReturnNil` が 72%」という一見それらしい結果**が出ていた
  （実際は `CallMethod` が 99.95%）。帰属は**独立な解析値**と突き合わせること
  （#50 では 500 万回の呼び出しベンチで `call − empty` の差分と照合した）。
- **⚠ op ごとに時計を読む方式でプロファイルしない**（#50）。安い op ほど相対誤差が大きくなり、
  「命令には値段の差がある」という**肝心の量が歪む**。**別スレッドからの統計サンプリング**なら
  サンプル数がそのまま滞在時間に比例する（計測ビルドの下駄は実測 0.95x ＝ 系統誤差なし）。
- **A/B は当該変更だけを切り替えて取る**（#21-b）。前回測定から時間が空いた値と比べると
  他の変更やマシン変動を誤って帰属する（`bench_field_access` の退行を #21-b のせいと誤認した実例）。
- **退行を疑ったら「そもそも触っているか」を先に見る**。`--vm=off` での切り分けは #33 で失われたので、
  **同じ 2 バイナリで測り直して再現するか** と「変更と同規模のプローブ」で判断する。
- **⚠ null 結果こそ「そもそも触っているか」を先に確かめる**（#46 では 2 バイナリの逆アセンブルを
  突き合わせ、変更が効いている経路を測っていることを確認してから捨てた）。
- **HEAD のバイナリが要る A/B・IR 比較では `git stash push -- src/` で退避** してビルドする。
  実行前に必ず `git status` を確認し、`src/` をスクラッチパッドへコピーしておく
  （過去に未コミット変更の破棄事故あり）。
- **⚠ `#[inline]` は効いているとは限らない**（#1-x）。巨大関数は LLVM が却下する。

- **⚠⚠ `flat_bench.ar` は配置ノイズだけで ±7% 動く**（#62）。`Cargo.toml` に `[profile.release]` が
  無い ＝ **`codegen-units = 16`（既定）・LTO 無し**なので、**コードをモジュール間で動かすだけで
  CGU 分配・インライン化・配置が crate 全体で変わる**。#62 では
  **`mod` 宣言の順序を逆にしただけ**のプローブが、リファクタリング本体と同じ **0.929x** を再現した
  （`bottleneck_bench.ar` は 0.969x で**完全一致**）。
  ⇒ **このベンチでリファクタリングの良し悪しを判断してはいけない。**
  ⚠ **「再現したから実差」は誤り**。再現性は必要条件でしかなく、**同規模プローブとの比較**が要る。
  ⚠ 敏感な理由は「25M 回の native↔解釈コールバック」という**境界支配**の形だから。
  ⇒ 疑わしい差が出たら **①同一 exe の負の対照 ②区間別の内訳 ③分散 ④同規模プローブ** の順に潰す。

## 2. VM / コンパイラを触るとき

- **`exec_op` は `#[inline(always)]`。op のアームに重い本体を書かない**（#10-b）。その op を
  使わない Chunk のホットループまで 4〜6% 遅くなる。逆に **全部外へ出すと** その op を使う側が
  7〜10% 損する。→ **IC はヒット経路だけインライン・ミス経路は `#[inline(never)]`**。
  （#48 で同じ罠を再演し 0.91x の退行を出した ＝ **判定を `Op::Call` のアームに直接書いた**。）
- **診断フックを実行経路に足すときは feature で消せる形にする**（#10-a）。`exec()` は文ごとに
  呼ばれるので `OnceLock` の atomic 読み 1 回でも **11% 退行** した
  （`cfg!(feature=..)` を先に見て定数 false にする）。
- **⚠ コード索引を持つ op を足したら `peephole::code_target_mut` に登録する**（#27-d）。
  `ForIter` の exit・`SetupTry` の handler・`StaticInit` の after。忘れても
  **テストも例題も通ってしまう**（たまたま除去対象が無かっただけ）。
- **⚠⚠ 採番はリゾルバと同順・同数**。`push_base` される名前は `slots` に入れなくても
  **必ず 1 slot 消費する**（`static` で飛ばして `LoadLocal` が範囲外を読んだ）。
- **同じ木を歩く walker が 2 つあるとずれる**。`compile_stmt` に文種別を足したら
  **必ず採番側（`collect_nested_decls`）も見る**（#27-c で 2 回踏んだ）。
- **⚠ `*_evaled` 版とずれた実装を作らない** — 実バグ 4 回。同じ判断をする 2 実装は
  片方を委譲に畳む。畳めないものは **不変条件をテストで固定** する。
  ⚠ #48 の実バグはこの形: **VM は評価済みの値で呼ぶ ⇒ `dispatch_native_evaled` に落ちる ⇒
  この経路は設計として書き戻しをしない**（引数の AST 式が無いと書き戻し先が決まらない）ため、
  `import[cpp-lib]` のプリミティブ out 引数（`double*`）が **黙って 0.0 を返していた**。
- **⚠⚠ `Vec<T>` を `Rc<[T]>` に変えると `.clone()` の意味が黙って変わる**（#45）。
  「中身の複製」から「**参照カウント加算**」になり、**コンパイルは通る**。スレッド送出経路
  （`deep_clone`）でこれをやると **#15 の穴（非アトミック参照カウント）が復活** する。
  該当は 5 箇所中 3 箇所。**型では守れないのでポインタ同一性を見るテストで固定** する。
  ⚠ **async の実地ストレスでは検出できなかった**（競合窓が狭い）。**決定的な検査を別に置く**。
- **⚠⚠ 最上位 Chunk キャッシュは `Stmt` の *アドレス* をキーにする**（#36）。載せた AST を解放すると
  アロケータが同じアドレスを再利用し、**別の文が前の文の Chunk を実行する**（REPL がブロックごとに
  AST を捨て、`let xs = …` が `let total = …` の Chunk を走らせた）。
  新しい入口は **AST を保持し続ける**。
- **⚠ 脱出制御を足すときは「オペランドスタック」と「ハンドラスタック」の両方を戻す**（#34）。
  `has_escape` は **文しか歩かない** のでブロック式の中の `break` を見落とす。`try` から跳ぶと
  `PopTry` を通らず **ハンドラが残り、ループを抜けた後の無関係な例外を横取りする**。
  検知には「**跳んだ後に別の例外を投げる**」例題が要る（跳ぶだけの例題では素通りする）。
- **⚠ 必ず失敗する文は bail せず `Op::Fail` で同じ文言を出す**（#34）。実行時エラーになると
  分かっている文（囲むループの無い `break`）を bail すると `VmForceError` になり、
  **本来のエラー文言が消える**。
- **⚠ VM は「解決情報が揃っている」前提**（#3/#36）。`resolve_program` ＋ `check_and_annotate` ＋
  `set_toplevel_globals` を供給しない入口では、正しいコードでも `VmForceError` になる。
  ⇒ **入口ごとに配線する責任がある**（`run_program`・REPL・テストヘルパー・モジュール本体）。
  ⚠ 例題は全部 `run_program` を通るので **例題だけ見ていても入口の穴に気づけない**。
- **⚠ worker スレッドは `Interpreter::new()` を作る**（#32）。**型注釈等を引き継がない** ので、
  親の設定を渡し忘れると **ゲートに穴が開く**（実際に開いていた）。
- **`Rc` を含む値をスレッドへ送る経路（async）では `deep_clone` が独立バッファを作ること**（#15）。
  回帰検知は [async_string_share.ar](../../../examples/async/async_string_share.ar)
  （**接触回数を減らすと検知力を失う**）。
- **注釈（`res`・型）は最適化ヒントであって意味論の根拠ではない**（#15e）。破ると
  「同じコードが書かれた場所で挙動を変える」（**実バグ 5 件**）。
  ⚠ `Resolution::Unresolved` は「シャドウが無い」を意味しない。判定は **実際の束縛／出自** を見る。

## 3. 検査網・ゲートの信用（**最も繰り返し踏んだ類型**）

- **⚠⚠ 検査網は「例題が踏む形」しか見ない**（#27/#34/#36/#33/#41 で **5 回** 踏んだ）。
  `force_gate` 0 件・`tw_control_flow` 0 は **例題が必ずその形を書いている前提** に乗っている。
  新しい判断をする前に、**その形の例題があるかを先に確かめる**。
- **⚠ `force_gate` 0 件は「その時の例題で 0」であって「言語全体で 0」ではない**（#34/#35）。
  **例題が無い言語機能はゲートに映らない**。単体テストだけが押さえている形が現に 11 件あり、
  そのうち 5 件は `VmForceError` で止まっていた。**新しい形を疑ったら例題を先に書く**。
- **⚠⚠ ゲートは「緑だと報告された」ではなく「自分で走らせて緑」を確かめる**（#30 発見・#44 修正）。
  `debug_session.ps1` は `6bf039c` から 5/5 赤いままで、しかも完了報告には「5 identical」と
  書かれていた。**修正とその golden を同じコミットで入れると、録り直し漏れがレビューでも
  気づかれない**。
  ⚠ さらに **「緑だった環境と同じとは限らない」**（#49）— 2 度目の赤は src も golden も無関係で、
  **コンソールのコードページ依存** だった（別マシンでは緑のまま通る）。
- **⚠⚠ 赤いゲートは「検知力が落ちる」のではなく「別物を検査する」**（#44）。`step_over_heavy` は
  BOM がコマンドを 1 つ食っていたせいで、**名前どおりの step-over に到達する前に終わっていた**
  （＝ずっと「step-over を検査しているつもり」だった）。
  ⇒ golden を録り直すときは **`-Update` の前に「違う」ではなく「正しい」ことを 1 値ずつ裏取りする**。
- **⚠ ゲートが「例題の書き方」に依存していないか疑う**（#36）。`toplevel_vm_candidate` が
  `!toplevel_globals.is_empty()` を条件にしていたため、**最上位に宣言の無いプログラム** は
  最上位が丸ごとツリーウォークだったのに `force_gate` 0 件のままだった。
  **負の対照が発火しないときは、まず配線を疑う**。
- **⚠ 既存ゲートは exit code しか見ない**（#47/#48）。FFI が **黙って間違った値** を返しても全部緑。
  ⇒ 値を検査する例題は **期待値と違えば `raise` する** 形で書き、
  **修正前バイナリで exit=1 になること（負の対照）を確認** する
  （[cpp_out_param_writeback.ar](../../../examples/interop/cpp_out_param_writeback.ar)）。
- **⚠ `force_gate` は例題ごとに最初の 1 件で止まる**（1 例題 = 1 原因ではない）。潰すたび測り直す。
  文言だけで bail と `vm_ineligible` は区別できないので `AR_TW_STATS` の両表を突き合わせる。
- **bail する形はツリーウォークが正しいとは限らない**（`for-target-shadow` で実バグ）。
  基準は `python -m impl_python` の出力（[compare_python_impl.ps1](../../../compare_python_impl.ps1)）。
- **ゲートスクリプトは `target/release` を見る**（`cargo build` の debug だけ見て「直った」と
  判断しない）。**`$ErrorActionPreference='Stop'` から `cargo` を呼ぶと進捗の stderr で終了
  エラーになる** ので、その呼び出しの間だけ `Continue` に落とす（`tw_stats.ps1` 参照）。

## 4. PowerShell / 子プロセス / エンコーディング

- **PowerShell 5.1 は BOM 無し `.ps1` を ANSI として読む**（日本語コメント入りは UTF-8
  **BOM 付き** 必須）。**Rust ソースの一括書き換えは Python で `encoding='utf-8'` を明示**
  （`Set-Content` は文字化けする）。
  ⚠ **そのスクリプトから日本語を `print` すると cp932 の `UnicodeEncodeError` で書き込み前に落ち、
  変更が丸ごと消える**。進捗表示は ASCII か件数だけにすること。
- **⚠⚠ 子プロセスへ stdin を流すときは `Process.StandardInput` を使わない**（#49）。
  .NET Framework の `Process.Start` は writer を `[Console]::InputEncoding` で作り
  `AutoFlush=true` を立てた時点で **preamble（BOM）を子へ書く** ⇒ **`Start()` が返った時点で
  もう入っている**。`.BaseStream` へ BOM 無しで書く手当ては **効かない**。
  手は 2 つ: **`cmd /c "exe < file"` のネイティブリダイレクト**
  （[repl_session.ps1](../../../repl_session.ps1)。stdout/stderr を分けられない）か、
  **起動直前だけ `[Console]::InputEncoding` を preamble 無しに差し替えて `finally` で戻す**
  （[debug_session.ps1](../../../debug_session.ps1)）。
  ⚠ **発火はコンソールのコードページ依存** なので、別のマシンでは緑のまま通る。
- **⚠ `ReadToEnd()` を stdout→stderr の順に逐次呼ぶと子とデッドロックする**（#34 で 1 時間停止・
  #38 で修正）。子が stderr のパイプ（既定 4KB）を埋めると書き込みでブロックし、親は stdout を
  待ち続ける。**必ず `ReadToEndAsync()` で同時に読む**
  （[scan_examples.ps1](../../../scan_examples.ps1) が手本）。
  症状は「**CPU 時間が伸びないまま生き続ける**」。
  ⚠ **普段の実行では踏まない**（子の stderr が数 KB を超えて初めて発火）ので、新しく子プロセスを
  起こすスクリプトを書いたら **`AR_VM_DUMP=1` を付けて回して確かめる**
  （`bench_branch.ar` で 7KB 出る ＝ そのまま負の対照になる・#38）。
- **⚠⚠ `ReadToEndAsync` でも足りない — 孫プロセスが生き残るとパイプが閉じない**（#58）。
  `import[js-proc]` は **node のブリッジを孫として起こし、それが arrow.exe より長生きする**。
  孫はパイプの**書き込み端を握ったまま**なので、`WaitForExit` が返った後の
  **`$task.Result` が永久に完了しない**（親は無限に待つ）。
  ⚠ **症状は §4 の逐次 `ReadToEnd` と見分けが付かない**（CPU 0 のまま生きている）が、
  **原因も直し方も別**。⇒ 見分け方は「**`arrow.exe` は既に消えているか**」
  （`Get-Process` に子が居らず node/dotnet だけ残っていれば孫の握りっぱなし）。
  手は **`Start-Process -RedirectStandardOutput/-RedirectStandardError` でファイルへ落として
  終了後に読む**（ファイルハンドルは孫が持っていても読み出しを妨げない・
  [compare_import_paths.ps1](../../../compare_import_paths.ps1)）。
  ⚠ [compare_bytecode.ps1](../../../compare_bytecode.ps1) が `js_proc_*` / `cs_proc_app` を
  skip リストに入れているのは**この理由**（当時は理由を書いていなかったので #58 で踏み直した）。
- **native exe の stderr を `2>&1` で受けると PS5.1 が ErrorRecord 化** して exit 0 でも失敗扱いに
  なる。`Start-Process -PassThru` の `ExitCode` も当てにならない
  （`System.Diagnostics.Process` を直接使う）。
- ⚠ `powershell -File` 経由だと `-Scripts a,b,c` が 1 要素に潰れる（`-Command` で呼ぶ）。
