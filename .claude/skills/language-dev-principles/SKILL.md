# Arrow の言語開発 — 設計原則と作業の型

Phase R（AST 解決層）＋ Phase V（バイトコード VM）の系列（#1〜#88）で**繰り返し役に立った**
知識のうち、**特定のタスクに紐づかない汎用的なもの**だけを集めてある。

> **姉妹スキルとの分担**（重複させない）
> - **[vm-pitfalls](../vm-pitfalls/SKILL.md)** … **実際に踏んだ失敗**の目録（「テストは通ってしまう」系）。
>   *やる前に読む*もの。⇒ ベンチを取る前・opcode を足す前・「緑だから大丈夫」と言う前。
> - **本スキル** … **こう作る／こう進める**という原則。*設計するとき・レビューするときに読む*もの。
> - 個別の失敗事例は本スキルに書かない（`vm-pitfalls` を指す）。番号 `#N` の詳細は

## 1. 健全性の原則（**言語の意味論を壊さないための境界**）

- **⚠⚠ 注釈は最適化ヒントであって意味論の根拠ではない。**
  型注釈・`Resolution`・インラインキャッシュは「**あれば速い**」だけで、
  **無くても正しく動く**ように書く。破ると「**同じコードが書かれた場所で挙動を変える**」という
  最悪の壊れ方になる（この系列で実バグ 5 件）。
  - ⚠ `Resolution::Unresolved` は「シャドウが無い」を意味しない。判定は**実際の束縛／出自**を見る。
  - ⚠ 合成 AST（テンプレート実体化・実行時生成）は `node_id: 0` / `Unresolved` のまま来る。
    **注釈テーブルの引き手は必ず「未採番」を防御する**（そうすれば「遅いが動く」に倒れる）。

- **⚠⚠ 記憶域の種類を混ぜない。** Arrow の実行時記憶域は **4 種類**あり、上限も寿命も別:
  | 記憶域 | 何に使うか | 縛り |
  |---|---|---|
  | ローカル slot | 関数フレームの変数・一時値 | `Chunk::n_locals` |
  | セル（`Rc<RefCell<Value>>`） | **可変な共有**（クロージャ捕捉） | `Chunk::n_cells` |
  | `static_cells` | `static mut`（span がキー） | — |
  | グローバル（`scopes[0]`） | 最上位宣言 | 索引キャッシュ |
  - **可変な共有は slot では表せない**（flat slot は `Value` 直値）⇒ セル表へ逃がす。
  - 索引の検査は**記憶域ごとに別の上限**で行う（1 つの上限でまとめると誤読を見逃す）。

- **⚠⚠ 採番するものが 2 系統あるなら「同順・同数」を不変条件として明示する。**
  リゾルバとコンパイラは**独立に**ローカル slot を採番する。ずれると
  **別の変数を読む**か**範囲外を読む**（どちらも黙って間違う）。
  ⇒ **デバッグビルドで突き合わせる**（`Compiler::local_slot` がコンパイル時、
  `verify_storage_indices` が Chunk 完成時）。**release では消える**ので速度に影響しない。

- **⚠ 「この形のときだけ載せる」条件を外すときは、理由を 3 通りに分類してから外す。**
  ①**2 実装の差**を吸収している ②**最適化の前提**を守っている ③**本当に未対応**。
  外し方がそれぞれ違うので、**分類せずに外すと壊れる**。

- **⚠ 実行入口は「解決情報が揃っている」前提。** 供給しない入口では**正しいコードでも落ちる**。
  ⇒ **配線は 1 箇所**にまとめ、**対で要るものは 1 つの関数で受け取り、個別 setter は private** にする
  （片方だけ渡して忘れる形をコンパイルエラーにする）。

## 2. ドリフトを「強制」で止める（**この系列で最も再利用価値が高い型**）

同じ木を歩く walker が 2 つあると**必ずずれる**。`_ => {}` で終わる walker は
**variant を足しても何も強制しない**ので、足した人が全部直したかは誰にも分からない。

### 2 段の強制（**これが仕掛けの全部**）

1. **列挙側の `match` を exhaustive にする**（`_` を書かない）
   ⇒ AST/命令に variant を足すと**まずそこがコンパイルエラーになる**。
2. **列挙結果を表す enum を、消費側が exhaustive に match する**
   ⇒ 種類を足した瞬間に**全消費者が止まり**、「この walker ではどう扱うか」を必ず決めさせられる。

### 現在そろっている強制点

| 問い | 唯一の定義 |
|---|---|
| この**文**はどの名前を束縛するか | `src/decl_names.rs`（`each_declared_name` ＋ `DeclOrigin`） |
| この**式**の直下に何があるか | `src/expr_walk.rs`（`each_subpart` ＋ `SubPart`） |
| この**文**の下にどの本体・部分式があるか | `src/stmt_walk.rs`（`each_subpart` ＋ `StmtPart`） |
| この **op** はどの記憶域索引を持つか | `vm/compiler/mod.rs`（`storage_operands`） |
| この **op** は飛び先を持つか | `vm/peephole.rs`（`code_target_mut`） |

### ⚠⚠ 強制には**守れない範囲**がある（3 つとも実際に踏んだ）

- **止まるのは 2 段目だけ。** 「**そもそも列挙し忘れる**」のは人間が読むしかない。
  ⇒ **畳む前に「元の N 実装が何を見ていたか」の表を機械生成して突き合わせる**。
- **exhaustive でも「分類の誤り」は防げない。** 網羅はしていても
  「この op は索引を持たない」と**間違って分類**すればコンパイラは黙っている。
  ⇒ **分類は名前ではなく doc（仕様の記述）から機械抽出して突き合わせる**。
  ⚠ キーワード一致は**否定表現を読めない**（「〜は持たない」も引っかかる）ので、
  候補は「**人間が 1 件ずつ判断するための入力**」。「言及しているが持たない」の受け皿を作る。
- **「新しく足す」側しか守らない。** **既存の登録を外す**側には別の網（単体テスト）が要る。
  ⇒ 登録した項目は 1 つずつ「**外したら落ちるか**」を実測する。落ちないならテストを足す。

### ⚠ 畳むときに出てくる「片方だけが見ていたもの」は 3 分類する

①**本当の取りこぼし**（広げるのが正しい）②**意図的な差**（残す。理由をコメントに書く）
③**現状観測できない潜在バグ**（触らない）。**「なんとなく揃える」が一番危ない。**

⚠ **順序に意味がある列挙は種類を分ける**（`for` ターゲット・`except as` の別名など、
採番順が結果を変えるもの）。畳むと採番がずれる。

## 3. 「緑」の意味と、ゲートの選び方

### ⚠⚠ 全ゲート緑は「**例題が書いている形については緑**」という意味しかない

この系列で**5 タスクから実バグが出て**、**どれも「その形の例題が 1 本も無かった」**。
⇒ **`force_gate` 0 件は「言語全体で 0」の証明ではない。**

- **新しい構文・文脈を扱う前に `syntax_cov.ps1` を走らせる**（例題が一度も書いていない形を出す）。
  ⚠ 特に **`NESTED-GAP`（入れ子 `fn` の中に 1 度も書かれていない構文）** —
  歴史的な実バグ 5 件のうち 4 件がこの文脈だった。
- **VM の適格範囲を広げたら、その形の例題を必ず足す**（「動くようになった」の唯一の証拠）。
- 値を検査する例題は**期待値と違えば `raise` する**形で書く
  （既存ゲートの多くは exit code しか見ないので、**黙って違う値**を返しても緑になる）。

### 触った場所 → 見るゲート

⚠ 実体は **[scripts/](../../../scripts/)**（`./scripts/<name>.ps1` で呼ぶ）。
一覧と「いつ走らせるか」は [CLAUDE.md](../../../CLAUDE.md)、引数と既知の罠は
[BYTECODE_VM_PLAN.md](../../../implementation_logs/BYTECODE_VM_PLAN.md) の script 表。

| 触った所 | 主検査 |
|---|---|
| VM コンパイラ（生成コードが変わりうる） | `compare_bytecode.ps1`（byte-identical） |
| 解釈側（`eval_*` / `exec_*`） | `compare_outputs.ps1`（bytecode は自明に一致してしまう） |
| ネイティブ codegen | `dump_native_ir.ps1` の **IR byte-identical**（最強） |
| VM の適格範囲 | `tw_stats.ps1`（ツリーウォークが定義文だけか） |
| 対話 REPL / デバッガ | `repl_session.ps1` / `debug_session.ps1`（**stdin を与えるのはこれだけ**） |
| 識別子の改名・削除 | `stale_doc_refs.ps1`（**必ず**。作っただけでは守られない） |
| 意味論そのもの | `compare_python_impl.ps1`（参照実装との突き合わせ） |

⚠ **ゲートは「緑だと報告された」ではなく「自分で走らせて緑」を確かめる。**
⚠ **release バイナリを見る**（`cargo build` の debug だけ見て「直った」と判断しない）。
⚠ **数値の基準は文書を信用せず、同じセッションで HEAD を stash して測り直す**
（同じ時点について 3 通りの数字が併存していた実績あり）。**総数ではなく増分 0 を見る。**
⚠ **リファクタ後はテスト件数を前後で比べる**（合否だけ見ていると、テストごと消しても気づけない）。

## 4. 何をやるか・やらないかの決め方

- **⚠⚠ 推測せず先に計測する。** この系列で見積もりは何度も外れた。
  - **命令数は「当たりを付ける」用で「速度の予測」には使えない**。
  - **「exec が N 倍」は「全体が N 倍」ではない** — 段別分布を取ってから話す。
- **⚠ 「手写しだから畳む」ではなく、差を 1 つずつ測って理由を確かめてから畳む。**
  複数の実装が同じことをしているように見えても、**畳んではいけない差が同数混ざっている**ことがある。
  ⇒ 表にして「理由の無い差」と「理由のある差」に分け、**前者だけ**畳む。
- **速度が出なくても、簡素化・強制の獲得が見込めるならメリットとして数える。**
  ⚠ 逆に「**速度も出ず複雑になる**」なら**実装済みでも捨てる**。
- **⚠ 高リスク低リターンと判断したらスキップして保留にし、理由を記録する**（勝手に大改造しない）。
  判定基準として実際に効いたのは「**消費者が居るか**」。
- **⚠ タスクの定義が目的に対して過剰なら、定義のほうを見直す。**
- **タスクは番号で管理する。** 番号の無い作業が出てきたら**新タスクとして昇格を提案**する。
  残タスクには**依存関係（前提）を必ず付ける** — 「前提が空欄＝今すぐ着手できる」が一目で分かるように。

### 計画文書の書き方（この系列で維持している規約）

1. **実装の詳細を計画書に書かない。** 書くのは「**実装したという事実**」と「**その手法**」だけ。
2. **詳細・実測値・判断の根拠は実装ログへ。** 計画書からはリンクのみ。
3. **必読部は行数上限を決めて守る。** 超えそうなら確定済み・履歴を区切り線の下か
   実装ログ、または**スキルへ移す**（この文書がその移動先の 1 つ）。

## 5. VM を触るときの設計上の制約（**変えると全体が遅くなる／壊れる**）

- **`exec_op` は `#[inline(always)]`。op のアームに重い本体を書かない。**
  その op を**使わない** Chunk のホットループまで遅くなる。
  ⇒ インラインキャッシュは**ヒット経路だけインライン・ミス経路は `#[inline(never)]`**。
- **診断フックは feature で消せる形にする。** `exec()` は文ごとに呼ばれるので、
  **atomic 読み 1 回でも 11% 退行**した実績がある。`cfg!(feature = ..)` を先に見て定数 false にする。
- **`Op` のサイズは固定されている**（不変条件をテストが守っている）。
  情報を足したくなったら **op に直接持たせず、Chunk の副表へ逃がす**
  （そうしないと**全命令が太る**）。
- **`LoadName` は関数本体で使えないが `LoadGlobal` なら使える。**
  根拠は「**`slots` に無い＝この関数のローカルではない**」がコンパイル時に確定していること。
- **⚠ op を足したら診断用 feature ビルドも通す**（既定ビルドでは消えるコードがあり、
  壊れていても普通のビルドでは気づけない）。
