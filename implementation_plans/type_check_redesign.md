# 静的型検査の再設計（仕様構想）

**状態**: 設計中（実装未着手）
**起票**: 2026-09-12
**前提文書**: [type_binding_enforcement_plan.md](type_binding_enforcement_plan.md)（個別バグ修正キャンペーン 0-1〜A-4 の記録）
**進捗計**: `scripts/type_obligations.ps1`（型義務 108 件・着手時点 **STATIC 36%**）

---

## 0. なぜ再設計するか（実測）

0-1〜A-4 で 16 件の型検査の穴を塞いだが、**同じ密度で穴が再生する**。原因を測るために
型義務を数え上げた（`src/ast.rs` の `Stmt` 40 / `Expr` 30 バリアントから機械的に導出）。

| 判定 | 件数 | 意味 |
|---|---|---|
| `STATIC` | 39 | 静的検査がある |
| `RUNTIME` | 26 | その実行経路を踏まなければ見逃す |
| **`NONE`** | **43** | **無検査**。黙って不整合な型が通る |

**静的に検査されているのは 36%。** 原因は 3 つで、どれも個別修正では閉じない。

### 原因① `Unresolved` が万能受容体

`type_matches_exact`（`type_check/type_utils.rs`）の冒頭が
`if *arg_ty == InferredType::Unresolved { return true; }`。
**1 箇所の推論漏れが下流の全義務を無効化する。** `NONE` の大半がこれに帰着する。

### 原因② 推論が「揃わなければ要素型を捨てる」— 捨てた形が何にでも適合する

`Expr::List`（`type_check/infer.rs:20-32`）は要素型が一致しないと素の `List` に落とし、
素の `List` は `is_list_like` 規則で `ListOf(任意)` と適合する。**捨てることが「何でも通す」になる。**
実測: `[1, "s"]` が `list[int]` にも `list[str]` にも `list[float]` にも通る。`Set`/`Dict` も同じ。

### 原因③ 検査が AST の地点ごとの手書きで、数え上げる仕組みが無い

`infer()` が「型を返す」と「部分木を歩いて診断を出す」を兼ねているため、
`self.infer(e);` と結果を捨てる書き方が**正当な場合と義務忘れの場合で区別が付かない**
（実測 **19 箇所**が結果を捨てている）。`InferredType` は `#[must_use]` でもないので
コンパイラは何も言わない。0-1〜A-4 で塞いだ 16 件はすべてこの形だった。

### 付随: 適合判定の独立実装が 4 本ある

| 実装 | 場所 | 用途 |
|---|---|---|
| `type_matches_exact` | `type_check/type_utils.rs` | 静的検査 |
| `value_matches_type_ann` | `interpreter/ops/typecheck.rs:133` | 実行時（注釈文字列） |
| `value_is_type` | `interpreter/ops/typecheck.rs:219` | 実行時（型名） |
| `TypeTag::matches` | `vm/op.rs:45` | VM 高速経路 |

すでに食い違っている（`Optional[` を実行時だけ受ける／`uint` の扱い）。

## 1. 決定事項

### D-1 型検査を 3 種に分ける 【決定】

煩雑化（度重なる仕様変更でコードが散ること）を防ぐのが目的。

| Kind | 内容 |
|---|---|
| **Kind 1** | 実型が期待型と**同一**、または期待型へ**自明キャスト可能**であること |
| **Kind 2** | 実型が期待型へ**アップキャスト可能**であること（trait / protocol / Intersection が期待型のとき） |
| **Kind 3** | 実型が、**オーバーロードされた演算子が許可する型**に合致する、またはそのクラスへアップキャスト可能であること |

**場所（検査地点）× 型の種類**で Kind を使い分ける（§2 の義務表）。

⚠ **方向はアップキャストのみ**（具体 → 抽象）。ダウンキャストは不許可。
実行時検査なしのダウンキャストは不健全で、現在も `let back: Impl = t`（trait 変数から
具体クラスへ）は静的に弾いている（実測）。この挙動を保つ。

### D-2 型検査は型式解決後に行う 【決定】

`alias` の展開・`new_type` の同定・テンプレートの具体化・`Intersection`/`Result`/`Union` の
構造化を**先に**済ませ、検査は解決後の型に対して一様に適用する。

⚠ これにより既存バグ **L-2** が閉じる。現在 `resolve_declared_type`
（`type_check/stmt/resolve.rs:184`）は `Intersection` と `Result` の注釈について
**「注釈自身の妥当性」だけ検査して右辺と照合せずに early-return** している
（`let v: Intersection[Alpha, Beta] = OnlyAlpha(..)` と `let r: Result[int,str] = 1.5` が通る。
ARG/RET では捕まるので、原因がこの関数であることの証拠になっている）。

### D-3 現在 `Unresolved` になっているものにも 3 分類を適用する 【決定】

⚠ そのため**先に推論を埋める**。下記 3 件は「決定できない」のではなく
**決定を試みていない**（情報は揃っている）。

| 式 | 現状 | 情報の在処 | 必要な変更 |
|---|---|---|---|
| `Box[str]("s")` | `Unresolved` | `call_check.rs:203` が `name` と `type_args` を**既に手元に持ち、引数検査に使っている**のに結果型だけ捨てる | `InferredType::GenericInstance { name, args }`（A-2 で新設済み）を組んで返す |
| `wrong`（`fn` を名前で参照） | `Unresolved` | `infer.rs:71` の `Expr::Ident` が**変数スコープだけ**を引く。レジストリの `fn_sigs` に引数・戻り値が揃っている | lookup 失敗時に `fn_sigs` を見て `InferredType::Function { params, return_type }`（既存）を返す |
| `Color.Red` / `.value` | `Unresolved` | `registry/builder.rs:227` は `enum_item_<name>` を `known_class_names` に入れるだけで `value` フィールドを登録しない。`.value` は言語規則として `int`（実行時 `build_enum_classes` が強制） | `enum_item_<name>` に `value: int` を登録し、メンバーを `NamedInstance("enum_item_<name>")` として返す |

⚠ `infer.rs:133` の `Expr::TemplateInstantiate` も `self.infer(base);` して `Unresolved` を返す。
⚠ これは §7 #6 の「難しい」という評価を**撤回**する。A-2 で `GenericInstance` と
置換表（`class_and_subst`）ができた時点で機械的な作業になっていた。

### D-4 暗黙キャスト不可なキャストは `=>` を強制する 【決定】

組み込みで許されていないキャストは**キャスト演算子の使用を強制**する。

⚠ これにより既存バグ **L-1** が閉じる。現在 `type_matches_exact` の末尾は
`__cast__[T]` を持つクラスを `T` として受理するが**変換を挿入しない**ため:

```arrow
class Conv:
    mut n: int
    fn __cast__[int](self) -> int:
        return self.n
let x: int = Conv(5)
print(x)        # <Conv object at 0x...>   ← int 変数に Conv が居座る
print(x + 1)    # TypeError: unsupported operand types for `Add`: object and int
```

**型検査が嘘をついている唯一の箇所。** 容器経由でも漏れる（`list[int]` に `Conv` が入る）。

### D-5 `+=` は加算演算子と代入演算子の**二回**の型検査を経る 【決定】

`x += v` の義務は「`typeof(x + v)` が `typeof(x)` へ代入可能」。
右辺 `v` を左辺型と照合するだけでは**両方向にずれる**（実測の反例）:

```arrow
class Vec:
    mut n: int
    fn __add__(self, let other: Vec) -> str:   # 戻り値が Vec ではない
        return "oops"
mut v = Vec(1)
v += Vec(2)
print(v)        # oops   ← Vec 変数に str が入る（現状は無検査）
```

⇒ 検査 1（Kind 3: `x + v`）→ 結果型 `R` → 検査 2（Kind 1: `R` → `typeof(x)`）。

### D-6 Kind 3 は「可否」だけでなく**結果型**を返す 【決定】

- **組み込み演算子**: 要素型を**合成**する
- **クラス**: `__add__` 等の**宣言戻り値型**を使う

⚠ 結果型が粗いと**正しいコードが落ちる**（実測で確認した要件）:

| 結果型の精度 | `list[int] += list[int]` | `list[int] += list[str]` |
|---|---|---|
| 素の `list` を返す | ⛔ 誤って弾く | ✅ 弾く |
| `list[int]` / `list[int\|str]` を返す | ✅ 通す | ✅ 弾く |

（`xs += ["s"]` が `[1, 's']` を黙って作るのは実測済み。検体 `B10`/`B11`）

⚠ 演算子メソッドは **15 種が実在**する:
`__add__ __sub__ __mul__ __mod__ __pow__ __eq__ __ne__ __lt__ __le__ __gt__ __ge__ __neg__ __contains__ __cast__ __call__`。
`__eq__`/`__ne__` が `==`/`!=`、`__contains__` が `in` を担うので、実測で `NONE` だった
`O4`/`O5`/`O8` は Kind 3 に自然に収まる。

### D-7 空のコレクションリテラルは `list[⊥]`（要素型は下端）とする 【決定】

⚠ **`list[Any]` では閉じない。方向が逆になる。** 実測:

| 代入 | 結果 |
|---|---|
| `list[int]` → `list[Any]` | ✅ 通る（アップキャスト） |
| `list[Any]` → `list[int]` | ⛔ **弾かれる** |
| `mut xs: list[int] = []`（現状） | ✅ 通る（D-1 で撤去する双方向特例のおかげ） |

`Any` は要素型の**上端**なので `list[Any]` は `list[int]` の**スーパータイプ**。
`[] : list[Any]` を `list[int]` へ入れるのはダウンキャストで、D-1 の方針では禁止される
⇒ **今通っているコードが落ちる**。必要なのは上端ではなく**下端**（⊥ / Never）で、
`list[⊥]` はあらゆる `list[T]` へアップキャストできる。

⚠ **`Any` を引数側でも万能にする案は採らない。** `list[Any]` → `list[int]` を通すと
`let xs: list[Any] = [1,"s"]; let ys: list[int] = xs` が通るようになる
（**現在は正しく弾いている** — 実測）。閉じている穴と引き換えになる。

⚠ `⊥` は `set` / `dict` / `tuple` にも要る（`{}` / `()`）。
⚠ 現在 `let xs = []` が通る（文書 `language-differences.md` は「空コレクションは明示的な
型付けが必要」と書いているが未実装）。`list[⊥]` を入れると「要素を足せない空リスト」に
なるので、`let xs = []` を**エラーにする**か `list[⊥]` のまま許すかを決める必要がある（§4）。

## 2. 義務表（設計の中核）

⚠⚠ **これが無いと再設計しても同じ密度で穴が再生する。** 原因③は「関係の判定」ではなく
「**問いを発していない**」ことだった。3 分類は「問われたときの答え方」を定義するが
「どこで問うか」は定義しない。実測した無検査の多く（`xs.append("s")` / `a[i] = v` /
`yield` / 可変長引数 / `static mut` / `except as`）はこの形。

### 2.1 実装上の強制（提案・要承認）

1. **役割を 2 関数に割る**（ユーザー提案）
   - `walk(e)` … 部分木を歩いて診断を出す。**戻り値なし**
   - `type_of(e) -> Type` … 型を返す。**`#[must_use]`**
   - `walk` が `type_of` を呼ぶ
   ⇒ 「型を取ったのに使わなかった」19 箇所はコンパイラが指摘する

2. **`walk` を AST バリアントに対して網羅的にする**
   - `match` の `_ => {}` を**禁止**し、全バリアントを明示的に列挙する
   - 各アームに「この地点の義務は (Kind, 期待型の求め方, 変換挿入地点)」または
     **`義務なし` を明示**させる
   ⇒ 新しい構文を足すとコンパイルが止まる（`add-syntax` の手当て表と同じ仕掛け）

⚠ 1 だけでは不十分。「期待型を取りに行かなかった」は 1 では捕まらない（`xs.append("s")` は
`walk` も `type_of` も正しく呼べていて、期待型を求める処理が**存在しない**だけ）。
**2 が必須。**

### 2.2 場所 × Kind

| 場所 | Kind | 期待型 | 備考 |
|---|---|---|---|
| `let` / `mut` / `const` / `static` の束縛 | 1（期待型が trait/protocol なら 2） | 注釈、なければ推論型 | ⚠ 注釈が無くても同じ厳格さ（D1 の方針） |
| タプル分解束縛 | 1 | 位置ごとの要素型 | 現状 ✅ |
| `for` のループ変数 | 1 | 反復対象の要素型 | 現状 ✅ |
| 再代入 `x = v` | 1 / 2 | 束縛時の型 | 現状 ✅ |
| 複合代入 `x <op>= v` | **3 → 1** | D-5 の二段 | 現状 `NONE`/`RUNTIME` |
| フィールド代入 `o.f = v` | 1 / 2 | 宣言フィールド型 | 現状 ✅ |
| trait フィールド代入 `o::T.f = v` | 1 / 2 | 同上 | 現状**実行時のみ**（A-3 が捕まえている） |
| `static mut` クラス変数への代入 | 1 / 2 | 宣言型 | 現状 `NONE`（§7 #14） |
| フィールド既定値 | 1 | 宣言フィールド型 | 現状 ✅ |
| 添字代入 `a[i] = v` | 1 | 要素型 | 現状 `NONE` |
| 添字読み `a[i]` の添字 | 1 | `int`（`dict` は key 型） | 現状**実行時のみ** |
| 実引数 → 仮引数 | 1 / 2 | 仮引数の宣言型 | ⚠ **`mut` 引数は「同一のみ」**（§3） |
| 既定引数の値 | 1 | 仮引数の宣言型 | 現状 ✅ |
| 可変長引数の要素 | 1 | 宣言要素型 | 現状 `NONE` |
| 組み込みメソッドの引数（`append` 等） | 1 | 要素型 | 現状 `NONE` |
| `return` | 1 / 2 | 宣言戻り値型 | 現状 ✅ |
| `yield` | 1 | 宣言 yield 型 | 現状 `NONE` |
| `block_return` / `loop_yield` | 1 | `->T` 注釈 | 現状**実行時のみ** |
| 二項・単項演算子 | **3** | 演算子が許可する型 | 現状**実行時のみ**（`==`/`!=`/`in` は `NONE`） |
| `match` subject vs `case` パターン | **1（厳密同一）** | subject の型 | オーバーロード無しの比較と同じ扱い。現状 `NONE` |
| `if` / `while` の条件 | **未決**（§4） | `bool` か真偽性か | 現状 `NONE` |
| コレクションリテラル vs 注釈 | 1 | 合成した要素型 | ⚠ 原因②の修正が前提 |
| `cast` `=>` / `mustbe` | 検査ではなく**変換**（D-4） | — | 明示指定 |

### 2.3 型の種類 × Kind

| 型の種類 | 期待型に置いたときの Kind |
|---|---|
| プリミティブ（`int`/`float`/`str`/`bool`/`uint`/`complex`/`None`/`Undefined`） | 1 |
| コレクション（`list`/`set`/`dict`/`tuple`/`fixed_list`/`list_like`） | 1（要素型へ再帰） |
| 素のクラス（`NamedInstance`） | 1（Arrow はクラス継承を許さないので**完全一致**） |
| `trait` / `protocol` / `Intersection` | **2** |
| `new_type` | 1（基底と**別の型**。両方向とも不可） |
| `alias` | 1（**透過**。D-2 の解決で消える） |
| `enum` / `enum_item` | 1 |
| テンプレート実体（`GenericInstance`） | 1（型引数へ再帰） |
| `function[..]->T` | 1（**分散規則は未決** — §4） |
| `type[T]`（`TypeVal`/`TypeValOf`） | 1（`type[trait]` は 2） |
| `Union` / `Option` | 1（いずれかのメンバーに適合。**曖昧性規則は §4**） |
| `Result[T,E]` | 1（D-2 で L-2 が閉じる） |
| `Any` | 常に可（**上端**） |
| `⊥` | 常に可（**下端**・D-7） |

⚠ **クラス継承が無いことが完全一致判定の根拠**（`parser/classes.rs` が
`cannot inherit from ... (only traits are allowed as bases)` で弾く）。
クラス継承を入れるならこの行を継承チェーン探索へ変える（`FieldCheck` の doc にも同じ注意）。

## 3. 整合性検査とは別に「妥当性検査」を置く 【提案・要承認】

⚠⚠ 3 分類はすべて「**2 つの型が適合するか**」を答える。次はどれにも当てはまらないが、
実測で漏れている:

| 種別 | 実測した該当 | 現状 |
|---|---|---|
| **名前の存在** | `is NoSuchType`（死んだ腕 ＋ 腕の中のメンバーアクセスが全て無検査になる） | `NONE` |
| | `c.nope`（メンバー存在。「フィールドは全て宣言必須」なのに） | 実行時のみ |
| **個数** | 型引数の個数 `Box[int, int]` | `NONE` |
| | 実引数の個数 | ✅（既存） |
| **定義時の妥当性** | `enum` バリアント値が `int`（**未呼出関数内は無検査**） | `NONE` |
| | `Intersection` メンバーの相互両立 | ✅（既存） |
| | `Result` の ok ≠ err | ✅（既存） |

⚠⚠ **これは抽象的な懸念ではない。既存バグ L-2 がこの混同の産物である。**
`resolve_declared_type` の `Intersection`/`Result` の早期 return は
**「定義時の妥当性」を検査して満足し、整合性検査へ進まずに return している**。
2 つのカテゴリを同じ関数の同じ分岐で扱ったために、片方をやれば済んだ気になった形。

⇒ 設計に **「整合性検査（3 分類）」と「妥当性検査（存在・個数・定義時）」の 2 系統**を
明示的に置き、義務表の各エントリがどちらに属するかを書く。

### `mut` 引数は Kind 1 の「同一のみ」に縮退する

⚠ 推測ではなく**経験した失敗**。`mut` 引数は C ABI の `double*` 等で**書き戻し**が
起きるため、そこで `int → float` を許すと格納形式の型双parse になる。0-B2 で
`cpp_prim_ptr_int_arg_type_mismatch` を落とし、`param_type_matches` が `mut` 引数だけ
`type_matches_exact` を使うことで回避している。
⇒ Kind 1 は一枚岩ではなく、**別名性／書き戻しの有無で「同一のみ」に縮退する**。

### 許した非同一関係には「変換を挿入する地点」が必ず必要

⚠ L-1（`__cast__`）の本質。**許可する関係の表**と**各関係の変換を行う地点**を
1 対 1 で持たせる。対応が無い行は「受理するが変換しない」＝型検査が嘘をつく状態。
⚠ `fixed_list → list` を許すなら `Value::FrozenList` → `Value::List` の実変換が必要
（現在は**許していない** — 実測で変数束縛・引数のどちらも静的に弾かれる。許されているのは
`list_like` へだけ）。さらに `mut list` 引数へ渡すと凍結リストへの書き戻しになるので禁止。

## 4. 未決事項（判断が必要）

| # | 項目 | 判断材料 |
|---|---|---|
| **U-1** | **暗黙キャスト（`int → float`）を廃止するか維持するか** | **実測済み → 廃止が安い**（下表）。廃止すると Kind 1 が「同一のみ」になり、U-4 の曖昧性も消え、変換地点 33 箇所が 0 になる（「受理したなら変換地点がある」が自明に保たれる） |
| **U-2** | `if` / `while` の条件を `bool` 厳密にするか、Python 流の真偽性を採るか | 真偽性なら現状の `NONE` が正しい挙動。検体 `K1`/`K2` にその旨を書く |
| **U-3** | §3 の「妥当性検査」2 系統を設計に入れるか | 入れないと存在・個数・定義時の検査が再び失われる（L-2 が実例） |
| **U-4** | 期待型が `Union`/`Option` のときの曖昧性規則 | `let x: Union[float, int] = 1` は `int` と厳密一致しつつ `float` へ自明キャストも可能。「厳密一致優先 → 一意な自明キャスト → 複数候補ならエラー」など。**U-1 で廃止すればこの問題は消える** |
| **U-5** | `function` 型の分散規則 | `function[int]->int` に `function[Any]->int` を渡せるか（引数は反変・戻り値は共変が通例）。未定義のまま実装すると経路依存になる |
| **U-6** | `let xs = []`（注釈なしの空リテラル）を許すか | D-7 で `list[⊥]` になるので「要素を足せない空リスト」になる。`language-differences.md` は「空コレクションは明示的な型付けが必要」と書いているが未実装 |

## 5. 実装の前提（判断不要・要件）

| # | 要件 | 理由 |
|---|---|---|
| R-1 | **D-3 の推論 3 件を先に埋める** | 3 分類は受け取る実型が空だと効かない。どれも既存の部品で組める |

| R-3 | **原因②の修正**（コレクション推論を「捨てる」から「合成する」へ） | U-1 で廃止するなら `[1, 2.0]` は混在エラーで済むが、**維持するなら `list[float]` を合成しないと正しいコードが落ちる** |
| R-4 | **絞り込み（narrowing）を式でも効かせる** | `is` の絞り込みが `match` **文**では効くのに **式**では効かない（`Expr::MatchExpr`（`infer.rs:283`）が `check_match`（`stmt/check.rs:512`）の絞り込みを持たない）。文と式で意味論が違う |
| R-5 | **実行時 4 本の判定を 3 分類から導出する** | すでに食い違っている。3 分類を静的側だけに入れるとずれが 1 本増える |
| R-6 | **`FieldKind::StaticMut` を可変として数える** | `registry/builder.rs:388` と `stmt/check.rs:371` の `matches!(kind, FieldKind::Mut)` が `StaticMut` を落とすため、インスタンス経由の代入が `cannot assign to immutable field` で塞がれる。**実行時は実装済み**（`attrs.rs:407`）＝層の食い違い（§7 #13） |
| R-7 | **protocol を容器の内側でも一様に扱う** | `list[Pr]` の束縛は偶然捕まるのに `Option[Pr]` の戻り値とフィールド代入は漏れる（`resolve_protocols` が容器の内側へ再帰しないため、経路によって「名前的比較」と「特例による無条件受容」に分かれる） |
