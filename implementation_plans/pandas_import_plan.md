# pandas を `import[py]` で読み込む — 妨げている要因と、シグネチャだけの AST・遅延 import

## 0. 妨げている要因（測定: Arrow `b6e1e2af`・pandas 2.2.0・CPython 3.12.2・2026-11-01〜02）

`import pandas` は pandas の `.py` 254 モジュールと C 拡張 42 本（`pandas._libs.*`）・numpy を読み込む。
「対処」の列の **[n-m]** は本書のタスク、**[別件]** は本書の外。

## 1. 方針（2026-11-02 に決定）

- **D-1** モジュールの情報を後から付け足せる仕組みを作る。**Python のモジュール（`.py`）に限る**。Arrow のモジュールでは
  許さない（読み込み中の import は今のまま誤り、名前空間は今のまま写し）。
- **D-2** `if TYPE_CHECKING:` の中の import は、相手のモジュールが**まだ読み込み終わっていなければ**（読み込み中を含む）
  シグネチャだけの AST を仮に作る。実体の AST は、`TYPE_CHECKING` の外の import が作る。
- **D-3** 関数・ブロックの中の import も、相手が読み込み終わっていなければシグネチャだけの AST を作る。実行時にその文に
  来て、相手がまだシグネチャだけなら、そこで本体を読み込む（遅延 import）。
- **D-4** 「まだ読み込み終わっていなければ」は**読み込み中を含む**。本体の直下の import でも、相手が読み込み中（循環）なら
  シグネチャだけの AST で代用し、実行時は途中まで初期化した名前空間を渡す（CPython と同じ）。
- **D-5** 遅延 import の実行時に、AST の変換・import の充填・名前の解決をもう一度行える仕組みを作る。
  注釈（`AstAnnotations`）は**作り直さず、注釈なしで実行する**（2 節 2.5 の計測で、簡単さと速さの両方を満たすと確かめた）。
- **D-6** 型検査はシグネチャだけの AST でも動くようにする。
- **D-7** 型の情報が途中で変わったら誤りにし、`import[py-int]` を使うよう促す。
- **D-8** シグネチャの作り方:
  - ファイルが無くてシグネチャを作れない → 場所で分ける（4 節の 1）:
    - `try` の中 → 静的には誤りにしない。実行時の `ModuleNotFoundError` を `except` に捕まえさせ、その処理に従う
    - `if TYPE_CHECKING:` の中 → 未解決のままにする。未解決のまま使われようとしたら誤り
    - それ以外 → 誤り
  - C 拡張 → `.pyi` からシグネチャを作る（本体を読み込めない件は別件）
  - 標準ライブラリ → `.py` があればそこから再帰的に型を作る
  - built-in のモジュール（`.py` が無い）→ 型は Arrow が内部に持つスタブで解決し、実行は `import[py-int]` に読み替える
- **D-9** 標準ライブラリの `.py` を読めるようにし、`typing` を読めるようにする。
- **D-10** 同じ名前の宣言が分岐ごとに違う型のとき（`if X: def f(a: int)` / `else: def f(a: str)`）は、**Union 型**にして
  どちらもあり得ることを型に書く（4 節の 2）。
- **D-11** ジェネレータ式は Arrow のジェネレータ（`gen`）に読み替える（2.7）。
- **D-12** `list.extend` と `set.update` を実装する。Arrow のソースからも使える。ジェネレータ式の対応より前の別タスクにする（5-1）。

## 2. 設計

### 2.1 モジュールの状態

| 段 | 状態 |
|---|---|
| 構文解析（静的） | 未読込 → **シグネチャのみ** → 読み込み中 → 読み込み済み（本体全体） |
| 実行時 | 未実行 → 実行中（**途中まで初期化した名前空間**・D-4） → 実行済み |

⚠ シグネチャのみの状態は**静的な情報だけ**。実行時にシグネチャを値として束縛することは無い（import 文を実行するときは
必ず本体を読み込んで実行する）。

### 2.2 import の場所ごとの扱い

| import の場所 | 構文解析 | 実行時 |
|---|---|---|
| 本体の直下 | 読み込み済みでなければ本体全体を読む。**読み込み中ならシグネチャのみで代用**（D-4） | 文に来たら実行。相手が実行中なら途中の名前空間を返す |
| `if TYPE_CHECKING:` の中 | 読み込み終わっていなければシグネチャのみ | 実行しない（`TYPE_CHECKING` は偽） |
| 関数・`try` / `if` / `with` / `for` の中 | 読み込み終わっていなければシグネチャのみ | 文に来て、まだシグネチャのみなら本体を読み込んで（2.5）実行してから束縛 |

- `TYPE_CHECKING` の中で束縛した名前は、型検査では `if` の外の注釈からも見える。実行時には束縛しない（CPython でも参照すると
  `NameError`）。
- 関数の中の import が束縛するのは関数のローカルな名前（モジュールの本体へ引き上げない）。
- 相手のファイルが無いとき（D-8）:
  - `try` の中 → その文を実行したときに `ModuleNotFoundError`。`except ImportError:` などに捕まり、その処理に従う
    （任意の依存の `try: import x` / `except ImportError: x = None` が CPython どおり動く）。
  - `if TYPE_CHECKING:` の中 → 束縛する名前を**未解決**にする。注釈に書いてあるだけでは誤りにしない。型検査がその型を
    必要としたとき（Arrow からその関数を呼ぶ・その型の属性を読む、など）に誤り。
  - それ以外 → 構文解析の誤り。

### 2.3 シグネチャの作り方

- **Python の構文木から宣言だけを取り出す**（関数・メソッドの本体は変換しない）。変換器が拒む構文（0 節の 7）があっても
  シグネチャは作れる。取り出すもの:
  - 本体の直下とクラスの本体の `def` / `class`（基底・デコレータの `@property` / `@classmethod` / `@staticmethod` を含む）
  - 注釈つきの代入（注釈の型）と注釈の無い代入（`Any`・7-27 の規則）
  - import（再エクスポート。相手はシグネチャで解く）
- 型は注釈どおり、注釈が無ければ `Any`（ffi_value_exchange_plan.md 7-27 の規則と同じ）。
- 同じ名前の宣言が分岐ごとに違う型なら、その名前の型は各分岐の型の **Union**（D-10）。分岐の中の `def` / `class` /
  代入 / import が対象。同じ型ならまとめて 1 つにする。
- **`.py` と `.pyi` は同じ抽出器**で読む。今の `extract_py_type_stubs`（行ベースの近似・`import[py-int]` 用）は
  この抽出器に置き換える（型を作る処理を 1 つにする）。
- ⚠⚠ **型を作るのは抽出器だけ**。本体全体を読んだモジュールでも、メンバーの型は抽出器で作る。シグネチャのみの道と
  本体全体の道で型が食い違わないための約束で、D-7 の検査はこれが前提。
- built-in のモジュール（`.py` も `.pyi` も無い。Windows の CPython 3.12 で 67 本: `sys`・`itertools`・`math`・
  `_collections`・`_functools`・`_io` など）は、Arrow に同梱したスタブ（`.pyi` の形）を同じ抽出器で読む。

### 2.4 型が途中で変わったとき（D-7）

- 比べるのは **Arrow から見えるメンバーの名前と型**（抽出器が作るもの）。
- 調べる時点:
  - 遅延 import で本体を読んだとき（構文解析の後にファイルが変わった、など）
  - 本体を実行し終えたとき（シグネチャに載っていた名前が無い、または種類が違う。関数のはずがクラスや値になっている、など）
- ⚠ Union 型（D-10）の名前は、実行後の値が Union のどれかに当たれば「変わった」としない。どれにも当たらないときだけ誤り。
- 誤りの文面: `ImportError: the types of module 'm' changed while it was being loaded (..); use import[py-int] m instead`

### 2.5 実行時の読み込み（遅延 import・D-5）

- 実行時から `src/parser/imports/` の読み込みを呼ぶ。手順は、変換 → 本体の直下の import の充填 → 名前の解決
  （`resolve_program`）。
  - ⚠ 名前の解決は省けない（VM は解決情報が無いと、正しいコードでも落ちる）。
  - ⚠ ファイルの読み込みは `import_fs` を通す。実行時の入口は CLI だけ（拡張は実行しない）。
- **注釈は作り直さない。** 計測（6.3）の結果:
  - 典型的な Python のコード（数値・浮動小数点のループ、リスト・辞書・メソッド呼び出し・文字列、各 30 万回）で、
    実験版（Python の本体の注釈を捨てる）と HEAD の速さは同じ。HEAD 0.887 s ／ 実験版 0.877 s（1.012x）で、
    負の対照（同じ exe 同士）は 0.998x。
  - バイトコードも完全に同じ。今の Python の本体には特化に効く注釈がそもそも付かない（先行宣言の `mut x = None` で型が
    決まらず、汎用の `BIN` 命令になる）。
  - ⇒ 注釈なしで実行するのが簡単で、速さも変わらない。⚠ 1-3（`None` → `Any`）の後も `Any` では特化しないので変わらない
    見込みだが、Python のコードに型の特化が入ったら測り直す。
- ⚠ 新しく作る AST のノードの番号が、今の注釈の表と衝突しないようにする（未採番か、続きの番号。注釈を引く側は未採番を
  防御済み）。
- ⚠ 読み込んだ AST は捨てない（VM の最上位チャンクのキャッシュが `Stmt` のアドレスを鍵にしている・REPL の `kept_asts`
  と同じ事情）。
- 本体を変換できなかった（変換の誤り）ときは、実行時の `ImportError`（`try` / `except ImportError` で捕まる）。

### 2.6 名前空間を後から付け足す（D-1・`.py` に限る）

- `NamespaceData` が `members` の写しを持たず、いつもモジュールの大域を読む（今の `live` を全部の名前に広げる）。
  CPython のモジュールの `__dict__` がモジュールの大域そのものなのと同じ形。
  - 読み込み中の名前空間でも、そこまでに定義した名前が見える（D-4）。
  - 後から足した名前も見える。
- 実行時の `ModuleState::Loading` に、途中の名前空間を持たせる。

### 2.7 ジェネレータ式（D-11）

変換器が、合成のジェネレータ関数へ持ち上げる（CPython と同じ形）。一番外側の反復元だけはその場で評価して引数で渡し、
`if` と 2 本目以降の `for` は本体の中で評価する。

```
(elt for x in it if c for y in it2)   →   gen __py_genexpr_N(_it):        # 式の前（囲む本体）へ持ち上げる
                                              for x in _it:
                                                  if c:
                                                      for y in it2:
                                                          yield elt
                                          __py_genexpr_N(iter(it))       # 式はこの呼び出しに置き換える
```

- `iter(it)` をその場で呼ぶので、反復できない値は作った時点で `TypeError`（CPython と同じ）。
- **持ち上げてよい位置の判定は、lambda 用（`UnsafeHoistGuard`）を使わない。** あの判定は「補助文を前に出すと評価の回数が
  変わる」位置（内包・`and` / `or` の右側・条件式の腕・`while` の条件）を禁じるが、ジェネレータ式で前に出すのは**定義だけ**
  （評価は一番外側の反復元だけで、その場に残る）なので、評価の回数は変わらない。
- ⚠ 本体が外側の内包の変数を参照する形は、前に出した定義から名前が見えないので明示的な誤りにする（pandas・標準ライブラリに 0 個）。
- クラスの本体の直下にあるものは、定義をクラスの外（モジュール）へ出す（CPython でも、ジェネレータ式の本体からクラスの
  本体の名前は見えない。pandas・標準ライブラリに 0 個）。
- 実測（6.5）: この形を Python のソースに手で書くと、遅延束縛・内包の中・無限の列・副作用のタイミング・
  `sum` / `any` / `all` / `max` / `min` / `sorted` / `list` / `tuple` / `set` / `dict` / `frozenset` / `next` で受け取ることが
  CPython と同じだった。⚠ 次の 3 つは先に直す（5-1〜5-3）:
  - `list.extend` / `set.update` が無い（pandas に `.extend(<ジェネレータ式>)` が 7 個）
  - `str.join` にジェネレータを渡すと黙って `''`
  - `for` のループ変数を捕捉する入れ子の関数が `VmForceError`（pandas に 3 個、標準ライブラリに 1 個）

## 3. タスク

各タスクで、例題（誤りの形は `_error` の例題も）を足し、次のゲートを走らせる:
`test_build_gate` / `scan_examples` / `force_gate` / `compare_python_impl` / `compare_wasm_frontend`（wasm を先に作り直す）/
`compare_import_paths`。型検査を触ったら `type_obligations`、識別子を改名・削除したら `stale_doc_refs` も走らせる。
src のファイルを作ったら codebase map を再生成し、型検査・構文解析を触ったら VSIX を作り直す。

## 4. 決定の記録（2026-11-02）

1. **ファイルが無いとき（D-8・2-7）**: pandas は関数の中・`try` の中・`TYPE_CHECKING` の中で、このマシンに入っていない
   依存を 22 種類読む（`numba`・`sqlalchemy`・`openpyxl`・`lxml`・`xlrd`・`odf`・`tables`・`bs4` など）。すべて誤りにすると
   `import[py] pandas` がそこで止まる。
   ⇒ **`try` の中は実行時の `ModuleNotFoundError` を捕まえさせて、その処理に従う。`TYPE_CHECKING` の中は未解決のままにし、
   未解決のまま使われようとしたら誤り。それ以外は誤り。**
2. **分岐ごとに違う型の宣言（D-10・2-8）**: 静的にどちらとも決められない。
   ⇒ **Union 型にして、どちらもあり得ることを型に書く。**
3. **ジェネレータ式（D-11・フェーズ 5）**: 2026-08-28（#17）に明示的な誤りにしたのは、当時のジェネレータが本体を最後まで
   実行してから返す方式で、式から定義を前に出す仕組みも無かったため。B13（遅延のジェネレータ）と項目 26（lambda の持ち上げ）で
   前提がそろったが、取り上げ直していなかった（PYTHON_CONVERTER_LOG.md に「再検討の価値あり」とある）。
   ⇒ **Arrow のジェネレータへ読み替える。`list.extend` / `set.update` は Arrow からも使えるようにし、別タスクとして先に行う。**
