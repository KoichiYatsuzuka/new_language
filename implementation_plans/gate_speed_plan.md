# ゲートの実行時間を縮める（例題の実行を 1 回にまとめる）

言語を変えるたびに走らせるゲート（[scripts/](../scripts/)）は、**同じ exe で同じ例題を同じ引数で何度も実行している**。
「毎回」の 3 本（`scan_examples` / `force_gate` / `compare_python_impl`）だけで同じ実行が 3 回あり、A/B 系・wasm の
突き合わせにも同じ形の重複がある。

本書は、**ゲートが実行するコードを例題と分けて専用のフォルダ `gate/` に書き下ろし**、それを **1 回ずつ実行して結果を
保存する共通ランナー**で走らせ、各ゲートを「保存した結果を読んで判定するだけ」にする計画書である。

- 起票: 2026-11-15（利用者の依頼: ゲートの実行が長く作業を止めている。1 つのプログラムで複数の検証ができないか）
- 調査: Arrow `61beb9d9`（0.6.0・release ビルド・Ryzen 5 5600X 6 コア 12 スレッド / Windows 11）
- 状態: 起票のみ。未決事項 2 件（U-4・U-5）。フェーズ 1 は未決事項を待たずに着手できる（フェーズ 2 は U-4・U-5 の後）
- 改訂: 2026-11-15 利用者の決定を反映した。
  - `impl_python` との突き合わせは凍結（D-9・U-1 は解決）。
  - ゲートが実行するコードは全部 `gate/` に専用に書き下ろす。例題のコードを流用してつなぎ合わせてよい。GUI は入れない。
    ベンチと対話は入れる（D-10・U-2 は解決）。これに合わせてフェーズを組み直した。
  - cpp-lib の中継 DLL のキャッシュは今の仕組みのまま使う（D-11・U-3 は解決）。
- 関連: [CLAUDE.md](../CLAUDE.md) のゲートの表、skill `vm-pitfalls`（§4 子プロセスの罠）、skill `language-dev-principles`
  （どの変更でどのゲートを走らせるか）、[BYTECODE_VM_PLAN.md](../implementation_logs/BYTECODE_VM_PLAN.md) のスクリプトの表
- 範囲外: ゲートの実行中に窓が出る件（利用者の指示で実行時間の後に扱う。分かっていることだけ 6 節に書く）

## 1. 決定事項

- **D-1 判定の規則は変えない。変わるのは対象（`examples/` → `gate/`）。** 正規化・判定の規則は各スクリプトの今のものを
  引き継ぐ。共通ランナーは、対象を切り替える前に**同じ `examples/` で古い実装と同じ判定を出すこと**を確かめる（4 節）。
  対象を切り替えるときは、`gate/` が `examples/` と同じ範囲を覆っていることを別に確かめる（D-12）。
- **D-2 既存のスクリプトは入口として残す。** `./scripts/scan_examples.ps1` などの名前・引数・出力の最後の行
  （`SCAN-DONE` / `FORCE-GATE: …` / `PYTHON-DIFF: clean`）は変えない。中身が「共通ランナーを呼んで、保存した結果を
  読む」になる。CLAUDE.md の表・skill の手順はそのまま使える。
- **D-3 実行と判定を分ける。** 共通ランナーは例題を実行して exit / stdout / stderr / 経過時間 / タイムアウトの有無を
  保存するだけで、合否を知らない。判定は各ゲートが保存した結果から出す。
- **D-4 保存先は `target/gate_results/`。** git の管理外で、`cargo clean` で消える。exe ごとのディレクトリに分け、
  名前は exe の内容のハッシュにする（パスや更新時刻にしない。同じパスに作り直した exe を取り違えないため）。
- **D-5 子の出力はパイプで受けずファイルへ落とす。** js-proc / cs-proc の孫プロセスがパイプを握って返らなくなる
  （`vm-pitfalls` §4・`compare_python_impl` が 7 時間止まった件）。共通ランナーは全例題でファイルへ落とす。
- **D-6 保存した結果を使ったことは必ず表示する。** 何件を実行し何件を保存から読んだかを毎回出す。保存を無視して
  全部実行し直す引数（`-Fresh`）を全ゲートに付ける。「緑でないのに緑」を保存の取り違えで起こさないため。
- **D-7 並列にするのは取り合いが無いと確かめた例題だけ。** 逐次に残す例題は一覧で持ち、理由をその場に書く。
  速度を測るスクリプト（`ab_bench` / `speed_modes` など）は対象外（並列にすると数字が変わる）。
- **D-8 実装は PowerShell 5.1 のスクリプトのまま。** 既存のゲートと同じ書き方（`System.Diagnostics.Process`・
  .NET の API でファイルを読む）にそろえる。別の言語の道具を足さない。
- **D-9 `impl_python` との突き合わせ（`compare_python_impl`）は凍結する**（利用者の決定・2026-11-15）。`impl_python/` は
  更新を止めているので、Python 実装を再開するまで「毎回」のゲートから外す。スクリプトと `$knownDiff` は消さずに残し、
  再開するときに方針を決め直す。
  - ⚠ CLAUDE.md はこのゲートを「意味論を守る唯一の網」としている。凍結の間、Rust と独立した実装との比較は無くなる。
    残るのは例題の中の検査（`raise` / `mustbe` で自分の結果を確かめる例題）と A/B 系の出力の比較だけ。
- **D-10 ゲートが実行するコードは、例題とは別のフォルダ `gate/`（リポジトリ直下）に専用に書き下ろす**（利用者の決定・
  2026-11-15）。
  - `examples/` のコードを流用し、つなぎ合わせて書いてよい。
  - **GUI は入れない。** GUI は C++ / C# のライブラリの機能の 1 つなので、C++ / C# との受け渡しを確かめていれば足りる。
    ⇒ 窓を出すコード・除外の一覧（`spider_*` / `cs_form_app` / `math_render` など）・`force_gate` の「窓を閉じて終わらせる」
    処理は `gate/` には要らなくなる。
  - **ベンチと対話（REPL・デバッガ）は入れる。**
  - 作業ディレクトリは実行するファイルのディレクトリに統一する（もとの U-2 の論点。`gate/` で決め直せるので 1 つにする）。
- **D-11 cpp-lib の中継 DLL のキャッシュは今の仕組み（`cpp_cache_isolation.ps1`）のまま使う**（もとの U-3）。
  - C++ のライブラリそのものは Arrow に依らない。exe に依るのは、Arrow がヘッダから**生成する**中継 DLL とシム
    （`ar_{stem}.dll` / `ar_{stem}_shim.*`）で、印（`ar_{stem}.syms`）は生成するコードのハッシュ。
  - 生成するコードが 2 つの exe で同じなら（FFI の橋渡しを触っていない変更の大半）キャッシュは同じで、入れ替えは
    起きない。違うときだけ今の仕組みが exe ごとに分ける。基準側の結果を保存しても、この動きは変えなくてよい。
- **D-12 `gate/` へ切り替える条件は、覆う範囲が `examples/` を下回らないこと。** `syntax_cov`（構文）と
  `type_obligations`（型義務）を `examples/` と `gate/` の両方で取り、`gate/` の側に新しい穴（`NESTED-GAP`・`NONE` /
  `RUNTIME` への後退）が無いことを見る。エラーの例題（`_error`・約 290 件）は、同じ誤りが `gate/` にあることを
  誤りの種類（`TypeErrorKind` など）の一覧で比べる。

## 2. 未決事項

- **U-1（解決・2026-11-15）** `impl_python` 側の保存のキー → 突き合わせそのものを凍結したので不要（D-9）。
- **U-2（解決・2026-11-15）** 作業ディレクトリの不一致 → `gate/` を作り、そこで 1 つに決める（D-10）。
- **U-3（解決・2026-11-15）** A/B 系の基準側を保存するときの中継 DLL のキャッシュ → 今の仕組みのまま（D-11）。
- **U-4 切り替えた後、`examples/` をどのゲートが見るか。**（フェーズ 2 の前に決める）
  - ゲートが `gate/` だけを見るようになると、`examples/` は `archived/` と同じく「壊れていても全ゲートが緑」になる。
    一方で「新しい文法には例題を作る」規則（`regulations.md`）は残り、例題は利用者が読む見本でもある。
  - 案 1（推奨）: `scan_examples` を今の形のまま残し、「毎回」からは外して、例題を触ったときとリリースの前に走らせる。
  - 案 2: `examples/` はどのゲートも見ない。
  - あわせて、新しい文法を足すときに `gate/` にも書く規則を `regulations.md` に足すかどうか。
- **U-5 `gate/` のコードが合否をどう示すか。**（フェーズ 2 の前に決める）
  - 今の `scan_examples` は exit が 0 かどうかしか見ておらず、出力が正しいかは見ていない（見ていたのは凍結する
    `compare_python_impl` と A/B 系だけ）。`_error` の例題は `scan` の対象外で、「期待した誤りで止まるか」はどの
    ゲートも見ていない。専用に書き下ろすなら、ここを決め直せる。
  - 案 1（推奨）: コードが自分で結果を確かめる（合わなければ `raise` して exit が 0 でなくなる）。誤りで止まるはずの
    ファイルは、先頭のコメントに期待する誤りの種類を書き（例: `# expect: StaticTypeError …`）、ランナーが stderr と
    照らす。⚠ D-1 の「判定の規則は変えない」より検査が強くなる。
  - 案 2: 今と同じ（exit が 0 かどうかだけ。誤りのファイルは `VmForceError` の有無だけ）。
  - つなぎ合わせる単位もここで決まる。静的な誤りは 1 つでファイル全体が止まるので、誤りのファイルは 1 件 1 ファイル。
    正常系はつなぎ合わせるほどプロセスの起動（1 回約 24 ms・例題の中央値は 59 ms）が減る。ただし 1 か所の失敗で
    後ろが実行されなくなるので、主題ごとに 1 ファイル程度を想定する。

## 3. タスク

番号はフェーズごと。前のフェーズが後のフェーズの前提。フェーズ 6・7 はフェーズ 5 の後なら互いに独立。

### フェーズ 1: 計測と前提の確認

- **1-1** 今のゲートの全体の時間を測って 5 節の表に書く（`test_build_gate` / `scan_examples` / `force_gate` /
  `compare_wasm_frontend`、A/B 系は同一 exe どうしで）。GUI の例題が窓を出すので、走らせる時刻を利用者に知らせてから。
  以後の各フェーズはこの数字と比べる。
- **1-2** `bench/bench_ab_native.ar` がタイムアウトする原因を調べる（古い `.arc`・ハング・単に長い）。`gate/` へ
  持っていくベンチに同じ問題を持ち込まないため。
- **1-3** `AR_VM_DUMP=1` を付けても exit / stdout と、stderr からダンプの行を除いた残りが変わらないかを全例題で
  確かめる（重複 ④ の前提）。同じ exe で 2 回実行して結果が同じにならない例題の一覧も取る（`async`・アドレスの表示・
  経過時間）。`gate/` のコードを書くときの注意になる。
- **1-4** 切り替えの基準を取る（D-12）: 今の `examples/` での `syntax_cov` / `type_obligations` の結果と、`_error` の
  例題が出す誤りの種類の一覧を保存する。

### フェーズ 2: `gate/` の形を決める

- **2-1** `gate/` の構成と規則を決めて `gate/README.md` に書く: ディレクトリの分け方（言語の機能・外部言語ごと・
  `bench`・`repl`・`debugger`）、ファイルの名前、合否の示し方（U-5）、誤りのファイルの書き方、逐次にしか走らせ
  られないコードの印（cpp-lib / `import[rs]` / js-proc / cs-proc。0.3 の 6 並列で落ちた 11 件の原因をここで特定する）、
  ベンチの繰り返しの回数。
- **2-2** `examples/` の扱い（U-4）を CLAUDE.md と `regulations.md` に書く。
- **2-3** 各主題で 1 本ずつ試しに書き（正常系・静的な誤り・実行時の誤り・cpp-lib・ベンチ・REPL）、2-1 の規則で
  足りるかを確かめる。

### フェーズ 3: 共通ランナー

- **3-1** 共通ランナー（`scripts/gate_run.ps1`・dot-source して使う関数の形）を作る。入力は exe・ファイルの一覧・
  環境変数・制限時間。ファイルごとに exit / stdout / stderr / 経過時間 / タイムアウトの有無を
  `target/gate_results/<exe のハッシュ>/` に保存する。保存済みなら実行しない（`-Fresh` で実行し直す）。全部に
  `CreateNoWindow` を付ける。タイムアウトしたら子プロセスごと止める（`taskkill /T`）。この段階では逐次。
- **3-2** `scan_examples` と `force_gate` の判定を、保存した結果から出す形で書く。対象のフォルダは引数で渡せるように
  する。**まず `examples/` を対象にして、古いスクリプトと同じ判定が出ることを確かめる**（4 節）。
- **3-3** U-5 で案 1 にした場合、期待する誤りとの照合をランナーの判定に足す。
- **3-4** 並列の実行を入れる（既定の数は論理コアの半分。`-Jobs 1` で逐次）。逐次の印が付いたファイルは逐次。
  並列と逐次で保存される結果が同じことを、5 回繰り返して確かめる。

### フェーズ 4: `gate/` のコードを書く

1 タスクごとにコミットする。各タスクの終わりに、その範囲の `syntax_cov` / `type_obligations` / 誤りの種類が
1-4 の基準を下回らないことを見る（D-12）。

- **4-1** 言語の中核（`basics` / `collections` / `classes` / `typing` / `exceptions` に当たる範囲）の正常系。
- **4-2** 同じ範囲の誤り（静的・実行時）。
- **4-3** `async`。同じ exe で 2 回実行して結果が変わらない書き方にする（1-3 の一覧）。
- **4-4** 外部言語: C / C++（cpp-dll / cpp-lib）。GUI のライブラリ（DxLib）は使わない。
- **4-5** 外部言語: C#（cs-dll / cs-proc）と JS（js-proc）。フォームは使わない。
- **4-6** 外部言語: Python（`import[py]`）と Rust（`import[rs]`）。
- **4-7** import とモジュール（パッケージ・相対 import・再エクスポート・`.arc`）。`compare_import_paths` の 13 例題に
  当たる範囲を含める。
- **4-8** ベンチ。合否のゲートとして走らせる回数にする（今は 23 件で 82 秒。計測は `ab_bench` / `speed_modes` の担当）。
- **4-9** 対話: REPL とデバッガの golden（`repl_session` / `debug_session` が読むもの）。

### フェーズ 5: ゲートを `gate/` へ切り替える

- **5-1** D-12 の条件を全体で確かめる（`gate/` と `examples/` の覆う範囲の比較）。足りないところを書き足す。
- **5-2** `scan_examples` / `force_gate` の対象を `gate/` にし、2 本をまとめて走らせる入口
  （`scripts/gates_every_time.ps1`）を作る。`test_build_gate` → 実行 1 回 → 2 つの判定。1 本でも落ちたら exit 1。
- **5-3** `compare_python_impl` を凍結する（D-9）。スクリプトの先頭に凍結の理由と日付を書く。
- **5-4** 全例題を再帰で舐めるゲート（`syntax_cov` / `type_obligations` / `tw_stats` / `compare_tm_grammar`）の対象を

## 4. 検証の方針

ゲートそのものを書き換えるので、**新しいゲートが古いゲートと同じ判定を出すこと**を、置き換えるたびに確かめる。

- **共通ランナー（3-2）**: 対象を `examples/` にして、同じ exe で古いスクリプトと新しい実装の出力（`FAIL` /
  `TIMEOUT` の行・`VmForceError` の一覧・件数）を比べる。
- **`gate/` のコード（フェーズ 4・5-1）**: 覆う範囲が `examples/` を下回らないこと（D-12）。
- **正の対照**: 落ちるはずの状態を作って、新しいゲートが落ちることを見る。
  - `scan`: 例外で終わるファイル・自分の検査で `raise` するファイルを一時的に足す。
  - `force`: stderr に `VmForceError` を出す exe（または保存した結果を書き換える）。
  - 期待する誤り（U-5 の案 1）: 誤りが出ないファイル・別の誤りが出るファイルを一時的に足す。
  - 保存: exe を作り直したら保存を使わないこと。
- **負の対照**: `-Fresh` で全部実行した結果と、保存から読んだ結果が同じ。
- 並列（3-4）は 5 回繰り返して判定が変わらないこと。
- ゲートは `target/release` を見る。自分で走らせて緑を確かめる（CLAUDE.md）。

## 5. 見込み（推測。1-1 と各フェーズの実測で置き換える）

| | 今 | フェーズ 5 の後（推測） |
|---|---:|---:|
| 「毎回」のコードの実行回数（Rust 側） | 3 回 | 1 回 |
| 「毎回」の `impl_python` の実行 | 約 700 件 × 170 ms 以上 | 0（凍結・D-9） |
| 「毎回」のゲートの合計 | 未計測（`scan` だけで 156 秒） | 1 分前後 |

- つなぎ合わせでプロセスの数が減る分（例題の中央値 59 ms のうち起動が約 24 ms）と、GUI・タイムアウトが無くなる分、
  並列の分が効く。下限は逐次に残す外部言語のコード（cpp / rs / js / cs）とベンチで決まる。
- A/B 系は 4 回の実行が 1 回になる（基準側は最初の 1 回だけ）。wasm は 85 秒の大半が消える見込み。
- ⚠ フェーズ 4（コードの書き下ろし）がこの計画でいちばん大きい作業になる（今の例題は 9 カテゴリで約 720 件）。

## 6. 本計画でやらないこと

- **窓が出る件を単独で扱うこと。** `gate/` に GUI を入れず（D-10）、共通ランナーが全部に `CreateNoWindow` を付ける
  （3-1）ので、切り替えた後は窓が出なくなる見込み。切り替えるまでの間の今のスクリプトは直さない（利用者が先に
  直したい場合は別に扱う）。
- **覆う範囲を減らすこと。** `gate/` は `examples/` と同じ範囲を覆う（D-12）。減るのは GUI（D-10）と `impl_python`
  との突き合わせ（D-9）、ベンチの繰り返しの回数（4-8）だけ。
- **`impl_python/` の変更と、`impl_python` との突き合わせの再開。** 更新を止めている（D-9）。
- **速度を測るスクリプト**（`ab_bench` / `speed_modes` / `prof_dist` など）の変更。
- **`cargo test` そのものを速くすること。**
