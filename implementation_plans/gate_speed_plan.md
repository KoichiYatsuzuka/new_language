# ゲートの実行時間を縮める（例題の実行を 1 回にまとめる）

言語を変えるたびに走らせるゲート（[scripts/](../scripts/)）は、**同じ exe で同じ例題を同じ引数で何度も実行している**。
「毎回」の 3 本（`scan_examples` / `force_gate` / `compare_python_impl`）だけで同じ実行が 3 回あり、A/B 系・wasm の
突き合わせにも同じ形の重複がある。

本書は、**例題を 1 回ずつ実行して結果を保存する共通ランナー**を作り、各ゲートを「保存した結果を読んで判定するだけ」に
する計画書である。ゲートが**何を検査するか**は変えない。変えるのは実行の回数と順序だけ。

- 起票: 2026-11-15（利用者の依頼: ゲートの実行が長く作業を止めている。1 つのプログラムで複数の検証ができないか）
- 調査: Arrow `61beb9d9`（0.6.0・release ビルド・Ryzen 5 5600X 6 コア 12 スレッド / Windows 11）
- 状態: 起票のみ。未決事項 3 件（U-1〜U-3）。フェーズ 1・2 は未決事項を待たずに着手できる（2-5 だけ U-1 の後）
- 関連: [CLAUDE.md](../CLAUDE.md) のゲートの表、skill `vm-pitfalls`（§4 子プロセスの罠）、skill `language-dev-principles`
  （どの変更でどのゲートを走らせるか）、[BYTECODE_VM_PLAN.md](../implementation_logs/BYTECODE_VM_PLAN.md) のスクリプトの表
- 範囲外: ゲートの実行中に窓が出る件（利用者の指示で実行時間の後に扱う。分かっていることだけ 6 節に書く）

### 0.2 重複

| # | 重複 | 根拠 |
|---|---|---|
| ① | `scan_examples` の実行は `force_gate` に丸ごと含まれる | `force_gate` は `--vm=force` を渡していない（#33 以降、既定の実行が force と同じ）。違いは作業ディレクトリ（`scan` はリポジトリ直下・`force` は例題のディレクトリ）と対象（`force` は `_error`・GUI・`practical_examples` も実行する） |

## 1. 決定事項

- **D-1 検査の内容は変えない。** 対象の例題・除外の一覧・正規化・判定の規則は各スクリプトの今のものを引き継ぐ。
  新しい実装は、古い実装と**同じ判定を出すこと**を確かめてから置き換える（4 節）。
- **D-2 既存のスクリプトは入口として残す。** `./scripts/scan_examples.ps1` などの名前・引数・出力の最後の行
  （`SCAN-DONE` / `FORCE-GATE: …` / `PYTHON-DIFF: clean`）は変えない。中身が「共通ランナーを呼んで、保存した結果を
  読む」になる。CLAUDE.md の表・skill の手順はそのまま使える。
- **D-3 実行と判定を分ける。** 共通ランナーは例題を実行して exit / stdout / stderr / 経過時間 / タイムアウトの有無を
  保存するだけで、合否を知らない。判定は各ゲートが保存した結果から出す。
- **D-4 保存先は `target/gate_results/`。** git の管理外で、`cargo clean` で消える。exe ごとのディレクトリに分け、
  名前は exe の内容のハッシュにする（パスや更新時刻にしない。同じパスに作り直した exe を取り違えないため）。
- **D-5 子の出力はパイプで受けずファイルへ落とす。** js-proc / cs-proc の孫プロセスがパイプを握って返らなくなる
  （`vm-pitfalls` §4・`compare_python_impl` が 7 時間止まった件）。共通ランナーは全例題でファイルへ落とす。
- **D-6 保存した結果を使ったことは必ず表示する。** 何件を実行し何件を保存から読んだかを毎回出す。保存を無視して
  全部実行し直す引数（`-Fresh`）を全ゲートに付ける。「緑でないのに緑」を保存の取り違えで起こさないため。
- **D-7 並列にするのは取り合いが無いと確かめた例題だけ。** 逐次に残す例題は一覧で持ち、理由をその場に書く。
  速度を測るスクリプト（`ab_bench` / `speed_modes` など）は対象外（並列にすると数字が変わる）。
- **D-8 実装は PowerShell 5.1 のスクリプトのまま。** 既存のゲートと同じ書き方（`System.Diagnostics.Process`・
  .NET の API でファイルを読む）にそろえる。別の言語の道具を足さない。

## 2. 未決事項

- **U-1 `impl_python` 側の保存のキーをどの細かさにするか。**（2-5 の前に決める）
  - 例題は別のファイル（`.ar` のモジュール・`.py`・ヘッダ）を import するので、例題ファイルだけのハッシュでは足りない。
  - 案 1: `impl_python/` 全体のハッシュ + `examples/` 全体のハッシュ。確実だが、例題を 1 つ足すと全件を実行し直す。
  - 案 2（推奨）: `impl_python/` 全体のハッシュ + 例題ファイル自身のハッシュ + 「直接は実行しないファイル」（サブ
    ディレクトリ・`.py`・ヘッダなど）全体のハッシュ。例題を足しても実行し直すのはその 1 件。ただし例題どうしが
    カテゴリ直下の別の例題を import していると取り違えるので、その形が無いことを先に確かめる。
  - どちらの案でも、`-Fresh` で全件を実行した結果と一致することを確かめる（4 節）。
- **U-2 作業ディレクトリをどちらにそろえるか。**（1-3 で調べてから決める）
  - `scan` / `python` / A/B 系はリポジトリ直下、`force` / `wasm` は例題のディレクトリで実行している。
  - import はエントリのファイルのディレクトリが基準なので結果は同じはずだが、相対パスでファイルを開く例題や
    `ar_config.json` の探し方で変わりうる。変わる例題があれば、その例題だけ両方で実行する。
- **U-3 A/B 系の基準側を保存するとき、cpp-lib の中継 DLL のキャッシュをどう扱うか。**（4-2 の前に決める）
  - 今は `cpp_cache_isolation.ps1` が exe ごとにキャッシュを分け、交互に切り替えている（7-34）。基準側を先にまとめて
    実行して保存する形にすると切り替えは 2 回で済むが、保存した結果を読むだけの回でも、キャッシュが「始める前の状態」
    のままであることを確かめる処理は残す必要がある。

## 3. タスク

番号はフェーズごと。前のフェーズが後のフェーズの前提。フェーズ 4・5 はフェーズ 2 の後なら互いに独立。

### フェーズ 1: 計測と前提の確認

- **1-1** 今のゲートの全体の時間を測って 5 節の表に書く（`test_build_gate` / `scan_examples` / `force_gate` /
  `compare_python_impl` / `compare_wasm_frontend`、A/B 系は同一 exe どうしで）。窓が出るので、走らせる時刻を利用者に
  知らせてから。以後の各フェーズはこの数字と比べる。
- **1-2** `bench/bench_ab_native.ar` がタイムアウトする原因を調べる（古い `.arc`・ハング・単に長い）。直せるなら直し、
  ゲートで走らせる意味が無いなら除外の一覧に理由つきで足す。黙って除外しない。
- **1-3** 重複 ①②④ の前提を実測で確かめる。
  - 作業ディレクトリが違っても exit / stdout / stderr が同じか（全例題。U-2 を決める）。
  - `AR_VM_DUMP=1` を付けても exit / stdout と、stderr からダンプの行を除いた残りが変わらないか（全例題）。
  - 同じ exe で 2 回実行して結果が同じにならない例題の一覧（`async`・アドレスの表示・経過時間）。今の各ゲートの
    除外・正規化と一致するはず。

### フェーズ 2: 共通ランナーと「毎回」の 3 本

- **2-1** 共通ランナー（`scripts/gate_run.ps1`・dot-source して使う関数の形）を作る。入力は exe・例題の一覧・環境変数・
  作業ディレクトリ・制限時間。例題ごとに exit / stdout / stderr / 経過時間 / タイムアウトの有無を
  `target/gate_results/<exe のハッシュ>/` に保存する。保存済みなら実行しない（`-Fresh` で実行し直す）。この段階では逐次。
  - `force_gate` の「タイムアウトしたら窓を閉じて正常終了させる」「kill した例題も stderr を読む」をここへ移す。
  - タイムアウトした例題は子プロセスごと止める（`compare_python_impl` の `taskkill /T`）。
- **2-2** `scan_examples.ps1` を保存した結果からの判定にする（exit が 0 でない・タイムアウト）。
- **2-3** `force_gate.ps1` を保存した結果からの判定にする（stderr の `VmForceError`）。`scan` に無い例題（`_error`・GUI・
  `practical_examples` など）だけが追加で実行される。
- **2-4** `compare_python_impl.ps1` の Rust 側を保存した結果から読む。
- **2-5** `impl_python` 側の出力を保存する（U-1 のキー）。保存先は exe に依らないので
  `target/gate_results/impl_python/`。
- **2-6** 3 本をまとめて走らせる入口（`scripts/gates_every_time.ps1`）を作る。`test_build_gate` → 実行 1 回 → 3 つの判定。
  各ゲートの結果の行をそのまま出し、最後に合否をまとめて 1 行で出す。1 本でも落ちたら exit 1。
- **2-7** 文書を直す: CLAUDE.md のゲートの表と注意書き、skill `language-dev-principles` / `vm-pitfalls`、
  `BYTECODE_VM_PLAN.md` のスクリプトの表。ファイルを足すので `generate-codebase-map.ps1` を走らせる。

### フェーズ 3: 並列に実行する

- **3-1** 6 並列で落ちた 11 件の原因を特定し、逐次に残す例題の規則を決める（中継 DLL のキャッシュを作る例題・
  `import[rs]`・js-proc / cs-proc・同じファイルへ書く例題）。規則は名前の一覧ではなく、できるだけ例題の中身
  （`import[..]` の種類）から決める。新しい例題が自動で正しい側に入るようにするため。
- **3-2** 共通ランナーに並列の実行を入れる（既定の数は論理コアの半分。`-Jobs 1` で逐次）。GUI の例題は逐次。
- **3-3** 並列と逐次で保存される結果が同じことを確かめる（全例題・5 回繰り返して 1 件も違わないこと）。違う例題は
  逐次の側へ移す。
- **3-4** `bench` の例題の扱いを決める。合否のゲートとして走らせるだけなら並列でよいが、82 秒の大半は計測のための
  繰り返しなので、ゲートでは回数を減らす引数を渡せないかを調べる。

### フェーズ 4: A/B 系

- **4-1** `compare_outputs` と `compare_bytecode` の実行を 1 回にする（`AR_VM_DUMP=1`。1-3 で変わらないと確かめた場合）。
  対象と除外は 2 本で違うので、判定の側でそれぞれの一覧に絞る。
- **4-2** 基準側（`-A`）の結果を exe のハッシュで保存する（U-3）。2 回目からは新しい exe の実行だけになる。
- **4-3** `compare_import_paths` の 13 例題を同じ仕組みに載せる。
- **4-4** 同一 exe どうしの負の対照（差分 0）と、わざと出力を変えた exe での正の対照（差分が出る）を取る。

### フェーズ 5: wasm の突き合わせ

- **5-1** `dump_diags.js` がファイルの一覧を受け取り、1 プロセスで全部を解析して 1 行に 1 ファイルの JSON を出す形に
  する。ファイルごとに `setHostCwd` を呼ぶ。拡張も wasm を読んだまま複数のファイルを解析するので、実際の使われ方に近づく。
- **5-2** exe 側（`AR_CHECK_ONLY=1`）を共通ランナーで実行する（実行しないので並列にしやすい。ただし `import[rs]` は
  検査だけでもビルドが走るので 3-1 の規則に従う）。
- **5-3** 1 ファイルずつ起動する今の形と、診断が全ファイルで同じことを確かめる。前のファイルの状態が残って結果が
  変わる例題があれば、それは拡張の不具合なので別に報告する。

### フェーズ 6: 候補（フェーズ 5 の後に測って判断）

- **6-1** `type_obligations` / `annot_unresolved` を共通ランナーに載せる（重複 ⑦。`AR_CHECK_ONLY` の実行と環境変数を

## 4. 検証の方針

ゲートそのものを書き換えるので、**新しいゲートが古いゲートと同じ判定を出すこと**を、置き換えるたびに確かめる。

- 古いスクリプトを `_archive/` へ写してから書き換え、同じ exe で古い版と新しい版の出力（`FAIL` / `TIMEOUT` の行・
  `VmForceError` の一覧・`DIFFER` / `STALE` の行・件数）を比べる。
- **正の対照**: 落ちるはずの状態を作って、新しいゲートが落ちることを見る。
  - `scan`: 例外で終わる例題を一時的に足す。
  - `force`: stderr に `VmForceError` を出す exe（または保存した結果を書き換える）。
  - `python`: 出力の違う例題を一時的に足す。`$knownDiff` に載っていて一致する例題（`STALE`）も。
  - 保存: exe を作り直したら保存を使わないこと・例題を書き換えたら `impl_python` 側を実行し直すこと。
- **負の対照**: `-Fresh` で全部実行した結果と、保存から読んだ結果が同じ。
- 並列（フェーズ 3）は 5 回繰り返して判定が変わらないこと。
- ゲートは `target/release` を見る。自分で走らせて緑を確かめる（CLAUDE.md）。

## 5. 見込み（推測。1-1 と各フェーズの実測で置き換える）

| | 今（推定） | フェーズ 2 の後 | フェーズ 3 の後 |
|---|---:|---:|---:|
| 「毎回」の例題の実行回数（Rust 側） | 3 回 | 1 回 | 1 回 |
| 「毎回」の `impl_python` の実行 | 約 700 件 × 170 ms 以上 | 変えた例題だけ | 同左 |
| 「毎回」の 3 本の合計 | 未計測（`scan` だけで 156 秒） | 3 分前後 | 1 分前後 |

- フェーズ 3 の後の下限は、逐次に残す `interop` の例題（cpp / rs / js / cs）と GUI の例題の時間で決まる。
- `bench_ab_native` の 45〜90 秒は 1-2 で消える見込み。
- A/B 系は 4 回の実行が 1 回になる（基準側は最初の 1 回だけ）。wasm は 85 秒の大半が消える見込み。

## 6. 本計画でやらないこと

- **窓が出る件。** 分かっているのは、`force_gate` だけ子プロセスに `CreateNoWindow` を付けていないことと、GUI の例題を
  実行するのは `force_gate` だけであること。共通ランナー（2-1）では全例題に `CreateNoWindow` を付けるが、GUI の例題が
  出す窓は残る。扱いは実行時間の後で別に決める。
- **検査の対象を減らすこと。** 例題を間引く・ゲートを省く形の短縮はしない（1-2 の `bench_ab_native` と 3-4 の `bench` の
  回数だけは、理由を書いたうえで判断する）。
- **`impl_python/` の変更。** 更新を止めている。
- **速度を測るスクリプト**（`ab_bench` / `speed_modes` / `prof_dist` など）の変更。
- **`cargo test` そのものを速くすること。**
