# ネイティブコードのオブジェクト操作を VM と同じ論理にする（フィールド・メソッド・生成・組み込み関数・値渡し）

速度調査（3 モード比較）で、`str`・`list`・入れ子のインスタンスを持つクラスを使うコードでは
**`--compile` したほうが非コンパイルより遅い**（6 区間中 4 区間で 1.28〜1.98 倍遅い）ことが分かった。
ネイティブコードは数値計算こそ 17〜380 倍速いが、オブジェクトに触れるたびにインタープリタへ
**名前の文字列つきで**問い合わせ直しており、その窓口が VM 自身の経路より 4〜11 倍遅い。

本書は、ネイティブコードのフィールド読み書きを **VM（バイトコード）と同じ論理（同じ関数・同じインライン
キャッシュ）** で行うように変え、あわせてメソッド呼び出し・値の受け渡し・生成と組み込み関数の名前引きを
なくす計画書である。調査中・実装中に見つかった**正しさの不具合 11 件**（§0.3）を前提タスクとして先に直し、
値渡しの**過剰な複製**（仕様では不要なもの）を両モードでやめる。

- 起票: 2026-10-25（速度調査の結果から）
- 調査: Arrow `326e112`（release ビルド、Ryzen 5 5600X / Windows 11）
- 状態: 未決事項なし。フェーズ 1〜4 完了（1-1〜1-9・2-1〜2-4・3-1〜3-3・4-1〜4-4）・フェーズ 5 着手（5-1 完了）
- 方針: 利用者の指示（2026-10-25）— フィールド読み書きは VM と同じ論理で行う。
  ほかは調査報告の方針 2（型検査の結果でレシーバを決めて直接呼ぶ）・3（`int`/`float` を箱詰めしない）・
  4（コンストラクタと組み込み関数を名前引きなしで呼ぶ）に従う
- 改訂: 2026-10-25 U-1〜U-3 を利用者の回答で決定（D-6〜D-8）。値渡しの不具合（§0.3 ⑤）を 1-5 に、
  過剰な複製をやめる作業をフェーズ 6 に起票した
- 改訂: 2026-10-25 実装中に見つけた束縛の不具合（§0.3 ⑥）を 1-6 に起票した。1-3 に反復の統一を、

  同じシンボルになりモジュール全体がネイティブにならないこと（§0.3 ⑨）と、コンパイル済みのメソッドが自分のクラスの

## 0. 何が起きているか

### 0.1 速度（壁時計、scale 5・7 回の中央値。複合型クラスの物体シミュレーション 256 体）

| 区間 | 非コンパイル | コンパイル済み | 主な処理 |
|---|---|---|---|
| k1 step | 0.94 s | **1.67 s** | `mut self` メソッド＋入れ子属性の読み書き |
| k2 energy | 0.58 | **0.74** | `let self` メソッドの連鎖 |
| k5 spawn | 1.00 | **1.55** | オブジェクト生成 |
| k6 boundary | 0.88 | **1.76** | 解釈側のループから `b.step()` |
| k3 / k4 | 0.73 / 0.96 | 0.46 / 0.36 | 速く見えるのは §0.3 ⑤ の不具合で複製を省いているため |

コンパイル済みの時間の内訳（区間の実行時間に対する割合）:
フィールド読み出しのコールバック **67〜74%**（k1/k2/k3/k6）、メソッド呼び出し 5〜22%、
生成・組み込み関数 25〜30%（k4/k5）、**ネイティブコード自身 0.1〜0.5%**。

1 操作の単価（コンパイル済み → 非コンパイル）: フィールド読み 156〜252 ns → 18〜42 ns、
名前によるメソッド呼び出し 288 ns、入れ子の読み `b.pos.x` 474 ns → 42 ns。

### 0.2 原因（コード上の位置）

| 原因 | 箇所 |
|---|---|
| ネイティブはフィールドを**名前で、キャッシュなしで**引く（`get_attr_val(obj, name, None)`）。VM は呼び出し箇所ごとの IC（`AttrCache`）で slot を直接読む | `native_api/callbacks.rs:407-445, 1118-1156` / `vm/run.rs:1217-1274` |
| 上の名前引きは毎回 `format!("::{attr}")` を確保し、trait 修飾名を探して全フィールドを線形走査する（読み 1 回の 35〜42%）。trait を持たないクラスでも空振りで走る | `eval/attrs.rs:133-137` |
| レシーバのクラスが分かるのは `self` と型注釈付き仮引数だけ。`self.pos.f()`・`for b in xs: b.f()` は**同じモジュールの関数でも**名前で `CB_CALL_METHOD`（1 回に String 4 本） | `llvm_codegen/expr.rs:748-754` / `callbacks.rs:1061-1114` |
| 型検査の注釈を使うのは `int`/`float` の葉のフィールド型だけ | `llvm_codegen/context.rs:80-109` |
| 直接呼び出しの引数・戻り値はすべてハンドル（`float` を毎回 `make_float`/`to_float`） | `llvm_codegen/expr.rs:949-1021`・`function.rs:53-75` |
| `self.hits += n`（`int` フィールド）が型を見ずに `CB_BINOP` | `llvm_codegen/stmt.rs:72-83` |
| `a or b` が比較結果をハンドル化して `CB_IS_TRUTHY` で 2 回往復 | `llvm_codegen/expr.rs`（短絡評価） |
| クラス生成・組み込み関数を `CB_GET_GLOBAL`（名前）＋`CB_CALL_FN` で呼ぶ | `callbacks.rs:467-487` |

実験（10 行の試作）: trait を持たないクラスでは `format!` と走査を飛ばすだけで、
コンパイル済みが k1 0.59 倍・k2 0.63 倍・k3 0.61 倍・k6 0.63 倍になった（非コンパイルは不変、
同一 exe 同士の対照は 0.96〜1.07）。それでも k1 は非コンパイルと同程度で、残りは IC が無いこと・
名前による呼び出し・箱詰めによる。

### 0.3 調査中に見つかった正しさの不具合（いずれもゲートは緑のまま）

| # | 症状 | 原因 |
|---|---|---|
| ① | **先読みしたフィールドが古くなる**: `fn after_inc(mut self) -> int: self.inc(); return self.n` が非コンパイル 1・コンパイル済み **0**。`bump(c)` の後の `c.n` も 10 → **0** | 先読みの条件 `body_writes_param`（`llvm_codegen/mod.rs:749`）が本体中の `p.attr = ..` しか見ない。`mut` の受け手はメソッド・関数経由で書き換わる |
| ② | コンパイル済みコードで **`range`・`print`・`repr`・`enumerate`・`zip`・`getenv` が実行時に `NameError`**（コンパイルは通る）。`len`・`str`・`int`・`float`・`bool` は動く | 組み込み関数を `CB_GET_GLOBAL` で「値」として引くが、これらはグローバルの値ではない（`callbacks.rs:467-487`） |
| ③ | 型付き読み出し `ar_get_float_field` / `ar_get_int_field` が**エラーを 0.0 / 0 に黙って置き換える**（アクセス違反・属性なしが消える） | `callbacks.rs:1134` / `:1154`（規約「掬いきれなかった選択肢はエラーにする」違反） |
| ④ | 書き込みが 2 実装（VM の `attr_assign_evaled` とネイティブの `set_attr_val`）。ネイティブ側は `static mut` への代入（インスタンス経由）が「has no field」で落ち、不変インスタンスの判定条件も違う。`import[rs]` 構造体の setter を扱わないのは意図的（中継コードが写しを更新する経路で、setter へ再入させない）。さらに生成コードは `obj::Trait.attr = v` の代入を**黙って出さず**、trait を実装したクラスの（自動生成の）`__init__` が trait のフィールドを設定しなかった（読むと AttributeError） | `eval/attrs.rs:381` / `:437`・`llvm_codegen/stmt.rs:61-84` |
| ⑤ | **コンパイル済みのメソッド呼び出しが `mut` の値を複製しない**（`let` 仮引数・`let self` とも）。呼ばれた側が受け取った値を返し、呼び出し元が後で元を書き換えると、非コンパイルでは変わらず、コンパイル済みでは**一緒に変わる**。関数呼び出しは複製する | メソッドの 2 経路（`ar_call_method` のネイティブ表からの直接呼び出し・モジュール内の直接呼び出し）が引数束縛を通らない（2026-07 に速度のため追加された際の取りこぼし） |
| ⑥ | **コンパイル済みコードの `let` / `mut` の宣言が複製しない**（2026-10-25 実装中に発見）。`mut q = o.inner; q.v = 7` が `o.inner` を書き換える。`let p = o.inner` の後で `o.inner` を書き換えると `p` も変わる。`mut ys = o.xs`・`let a = zs`（`zs` は `mut`）も同様 | VM は宣言の形で `StoreLocalDeepCopy`（`mut`）・`StoreLocalCopyFreeze`（`mut` の名前からの `let`）・`StoreLocalFreezeInstance`（式からの `let`）を出す（`vm/compiler/stmt.rs:151-166, 579-632`）が、ネイティブはどれも単なる格納 |
| ⑦ | **VM の関数本体で `let it = ys[0]` が `ys[0]` と共有する**（1-6 で発見）。最上位とツリーウォークは複製する（`[1]`）が、関数の中だけ `[1, 9]`。デバッガの `let dbg::x = e` も同じ | L2（`46b8d15`・式からの `let` は常に複製）が `exec_let` と最上位の `let_freeze_instance` だけを直し、関数本体の `StoreLocalFreezeInstance` と `vm_declare_debug` は `Instance` だけ複製したまま。複製が 6 箇所に手書きされていた |
| ⑧ | **コンパイル済みモジュールを取り込むと、モジュールの名前が取り込み側の大域に `let` で写される**（1-6 で発見）。取り込み側が同じ名前を宣言すると `NameError: variable 'G' is already declared`（非コンパイルでは動く）。コンパイル済みの関数が読む `G` も取り込み側のもの（同名があればそちら）で、`mut` の属性も失われる（`let a = G` が複製されない） | ネイティブの関数・メソッドはモジュールの大域へ切り替えずに走る（`NativeFnRef` が大域の番号を持たない）ので、`CB_GET_GLOBAL` が名前を引けるよう `try_load_native_module` が取り込み側の `scopes[0]` へ不変で写している（`exec/modules.rs:820-824`） |
| ⑨ | **同じ名前の定義が 2 つ以上ある（オーバーロード）と、モジュール全体がネイティブにならない**（2-3 で発見）。明示の `__init__` の引数がフィールドと違うと自動生成の `__init__` と並び、`invalid redefinition of function 'Vault____init___impl'` で clang が落ちる。`--compile` は「skipped」と出すだけで DLL の無い `.arc` を書き、実行は黙って非コンパイルになる | 適格判定（`eligible_fn`）がオーバーロードを見ず、シンボル（`method_symbol`）とネイティブのメソッドの表（`(クラス, 名前)` → 1 つ）が名前だけで決まる |
| ⑪ | **コンパイル済みコードのフィールドの複合代入が評価の順を違える**（4-2 で発見）。`self.n += self.bump()`（bump が n を書き換える）が非コンパイル 11・コンパイル済み **1**。受け手が呼び出しのとき（`self.pick().n += 5`）も、非コンパイルは読みと書きで 2 回評価するがコンパイル済みは 1 回 | ツリーウォーク（`attr_assign`）と VM は 右辺 → 受け手（読み）→ 演算 → 受け手（書き）の順だが、生成コードは受け手を先に読み、右辺を後に評価していた（`llvm_codegen/stmt.rs` の `AttrCompoundAssign`）。4-2 で同じ文を書き直すので一緒に直した |
| ⑩ | **コンパイル済みのメソッドが自分のクラスの private / protected のフィールドを読み書きできない**（2-3 で発見）。`self.secret = ..`（private）が `AccessError: 'secret' is private and cannot be accessed outside 'Vault'`（非コンパイルでは動く）。自動生成の `__init__` が private のフィールドを設定するだけでも落ちる | 実行時のアクセスの検査は `current_class` を見るが、ネイティブのメソッドの呼び出しはそれを設定しない（インタープリタは `run_vm_method` が受け手のクラスにする） |

**値渡しの規則**（`docs/spec.md:27-28`・`docs/grammar/02_variables.md:351-354`）: 複製するのは
**`mut` の値を `let` で受けるとき**だけで、`let` の値は共有する。今の実装との差は ⑤ のほかに
**過剰な複製**が 2 つある（結果は変わらず遅いだけ）:
非コンパイルの `let self` は受け手が `let` でも複製する（VM の呼び出し命令の `mut_mask` が引数の分しか無く、
受け手の可変性が分からないため・`vm/op.rs:225-272`）。コンパイル済みの関数呼び出しは引数が `let` でも
`let` 仮引数を複製する（`llvm_codegen/expr.rs:995-1011`）。

## 1. 決定事項

- **D-1 フィールドの読み書きは VM と同じ関数で行う。** IC の判定（命中経路）と格納の詰め方は
  `AttrCache`（`ast.rs:165`）と 1 か所で共有し、VM の `GetAttr` / `GetAttrLocal` / `SetAttr` と
  ネイティブのコールバックの両方がそれを呼ぶ。ネイティブは**属性アクセスの箇所ごとに IC のセル**
  （DLL 内の `u64`、初期値 0）を持ち、そのポインタをコールバックに渡す。外れたときは VM と同じミス経路が埋める。
  - セルは非同期タスクのスレッドと共有されうるので `AtomicU64`（Relaxed）で読み書きする。
    `class_id` はプロセス全体で一意（`value/core.rs:13-20`）で、スレッドへの複製も同じ id と
    `field_index` を保つので、命中した slot は正しい。
- **D-2 型検査の注釈はヒントとして使う**（`language-dev-principles` §1）。注釈でレシーバのクラスを決めて
  直接呼ぶときは、**実行時に class_id を照合するガード**を置き、外れたら従来の `CB_CALL_METHOD` に落とす。
  `list[T]` の要素型・`new_type` など、実行時に保証されない型があるため。
- **D-3 `int` / `float` はモジュール内では生値で受け渡す。** 箱詰めはインタープリタとの境界
  （`_tl` / `_typed`）だけで行う。
- **D-4 生成と組み込み関数は名前引きなしで呼ぶ。** 入口は VM の `Call`（クラス生成）・`CallBuiltin`
  （`vm/run.rs:1305`、同名のユーザー束縛があればそちらを呼ぶ判定を含む）と同じ関数にする。
- **D-5 既存の `.arc` は作り直さなくても動く。** `ArCallbacks`（`native_api/mod.rs:427`）へは
  **末尾にだけ**追加する（cpp / rs の中継コードが先頭部分を宣言しているため）。`_tl` / `_typed` の ABI は
  変えない。内部の `_impl` の ABI だけを変える。
- **D-6（U-1）書き込みにも IC を入れ、VM の `SetAttr` とネイティブの両方が同じ共有関数を使う。**
  今の VM の `SetAttr` は 1 回の代入で名前による表引きが約 6 回ある。IC が当たったときに省ける検査と
  省けない検査（可変性・不変インスタンス・格納時の型検査）を分けてから入れる。
- **D-7（U-2）先読みは `let` の受け手（`let` 仮引数・`let self`）だけにする。** 非コンパイルも入口で
  複製する（`mut` の値の場合）か、もともと書き換わらない（`let` の値の場合）ので、入口時点の値を使って
  意味論が一致する。`mut` の受け手は D-1 の IC で毎回読む。
- **D-8（U-3）値渡しは両モードとも規則どおりにする**: `mut` の値を `let` 仮引数・`let self` で受けるときだけ
  複製し、`let` の値と一時値は共有する。⑤ の不足（1-5）と、過剰な 2 つ（フェーズ 6）を直す。
  受け手・引数が `let` か `mut` かは**宣言で決まる**（注釈ではない）ので、実行時ガードは要らない。

## 2. 未決事項

なし（U-1〜U-3 は D-6〜D-8 で決定）。

## 3. タスク

各タスクで、仕様の正例と誤り例（`_error`）の例題を足す（規約）。値を確かめる例題は、期待値と違えば
`raise` する形にする。コンパイル済みの経路を確かめる例題は、モジュールを `--compile` した `.arc` を読む形にする。

## 4. 検証の方針

- 触る場所ごとのゲート（`CLAUDE.md`）: ネイティブ codegen → `dump_native_ir`（差分が対象関数だけか）。
  解釈側のコールバック・`attrs.rs` → `compare_outputs -A` と `compare_import_paths -A`（cpp / rs の中継コードも
  `ArCallbacks` を使う）。VM の命令（2-1・2-3・6-1）→ `compare_bytecode`。毎回 `test_build_gate`・`scan_examples`・
  `force_gate`・`compare_python_impl`・`stale_doc_refs`。
- 速度: `ab_bench_modes -A <直前のタスクのコミットから作った exe>`。数 % の差は、同じセッションで取った
  同一 exe 同士の対照と、同規模の摂動と並べて判断する（`vm-pitfalls` §1）。
- 例題の網: コンパイル済みモジュールの例題は今は少ない。各タスクで、**両モードで同じ値になること**を
  確かめる例題（モジュールを `--compile` して読む形）を足す。

## 5. 見込み（推測。各フェーズで実測して置き換える）

k1 の 1 体×1 ステップは、今はコールバック 53 回で 6.1 µs（非コンパイルは 3.5 µs）。
フィールド読み 23 回が 156〜252 ns → 30〜60 ns（VM の命中 18〜42 ns＋コールバックの固定費）、
名前によるメソッド呼び出し 2 回（288 ns）がガード付きの直接呼び出しに、箱詰め約 20 回が消えると、
**1.5〜2 µs 程度（非コンパイルの約 2 倍速）** を見込む。数値計算だけの区間は今と変わらない。
k3 / k4 は 1-5 でコンパイル済みも複製するようになるので、今の数字より遅くなる（規則どおりの費用）。

## 6. 本計画でやらないこと

- ネイティブからインスタンスのメモリを直接読む（ハンドルではなくポインタを渡す）方式。
  方針 1 を「VM と同じ論理」と決めたため。フェーズ 2 の結果を見て、なお遅ければ別に起票する。
- `mut` の受け手に `let self` メソッドを呼ぶときの複製そのものを安くする方法（コピーオンライト等）。
  規則どおりでも重い（調査の k3 で 54%）が、言語仕様の判断が要るので別に扱う。
